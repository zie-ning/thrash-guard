# 로그 링버퍼와 기록 스레드 설계

> 작성: 2026-11-11. 로드맵 M3-5a의 설계 기록이다. 데몬 전체 설계는 [overview.md](overview.md)에 있다.
> 코드 위치: `src/daemon/log.[ch]`. 수치는 모두 측정 전 임시값이며, 측정하지 않은 것은 "미확인"으로 표시한다.

## 1. 왜 필요한가

데몬은 스래싱 중에도 판단을 멈추면 안 된다. 그런데 스래싱 중에는 디스크가 포화되어 `write`가 오래 막힐 수 있다.
로그를 메인 루프가 파일이나 표준 오류에 직접 쓰면 판단 루프가 로그 때문에 멈춘다. 길벗 사건에서 관측 에이전트들이
먼저 멈춘 것과 같은 실패 방식이다.

로그를 위해 메모리를 새로 할당하는 것도 금지다(plan 4.4, 핵심 경로의 할당은 회수를 부를 수 있다).

그래서 로그를 두 단계로 나눈다.

```text
[메인 루프] --(메모리 복사만)--> [링버퍼] --(별도 스레드가 꺼내서)--> [표준 오류 / 파일]
   기다리지 않음                  고정 크기                         느려도 메인에 영향 없음
```

## 2. 요구사항과 비목표

| 구분 | 내용 |
|---|---|
| 요구 | 메인 루프의 로그 호출은 **어떤 경우에도 기다리지 않는다**(락, 디스크, 할당 없음) |
| 요구 | 초기화 이후 `malloc` 호출 0회(M3-6에서 검증). 기록 스레드도 포함 |
| 요구 | 로그 줄은 쓴 순서대로, 깨지지 않고 나간다 |
| 요구 | 한가할 때 기록 스레드는 완전히 잠든다(주기적 깨어남 없음) |
| 요구 | 버퍼가 가득 차면 새 로그를 버리고, **버린 개수를 반드시 기록**한다 |
| 비목표 | 강제 리셋 직전 로그의 디스크 반영 보장(§9 한계) |
| 비목표 | 로그 파일 로테이션, 로그 레벨 설정 키(M3 범위 밖) |
| 비목표 | 여러 스레드에서 동시에 로그를 쓰는 기능(§4의 단일 생산자 제약) |

## 3. 구성

```text
메인 루프 (생산자, 유일)                 기록 스레드 (소비자, 유일)
  tg_log_begin()    칸 확보 (가득 차면 false)   read(eventfd)  ← 평소 여기서 잠듦
  tg_buf_*()        칸 안에서 직접 줄 조립      while (tail != head) 칸을 꺼냄
  tg_log_end()      head 증가 → write(eventfd)    줄을 4 KiB 모음 버퍼에 이어 붙임
                                                  write(fd) 한 번 (가득 차면 중간에 비움)
                                                  tail 증가
```

- 링버퍼는 `calloc` 한 번으로 **초기화 때** 만든다. 이후 할당은 없다.
- 기록 스레드도 `stdio`를 쓰지 않고 `fmt.c`와 `write(2)`만 쓴다(할당 금지 유지).
- 스레드 스택은 64 KiB로 고정한다(로드맵 보완점 7).
- 기록 스레드는 모든 시그널을 막아 두어 시그널 처리는 메인 스레드만 한다.

## 4. 자료구조

### 4.1 슬롯

고정 크기 256바이트 슬롯을 쓴다. 가변 길이보다 단순하고, 가득 참 판정과 칸 번호 계산이 쉽다.

| 필드 | 크기 | 설명 |
|---|---|---|
| `ts_ns` | 8 | 쓴 시각(`CLOCK_MONOTONIC`, 나노초). 메인 루프가 `publish` 직전에 찍는다 |
| `len` | 2 | 본문 길이 |
| `level` | 1 | 0=ERR, 1=WARN, 2=INFO, 3=DEBUG |
| 예약 | 1 | 0 |
| `text` | 244 | 본문. `tg_buf` 규약(NUL 자리 포함)에 따라 **본문은 최대 243바이트**다. 읽을 때는 `len`을 쓴다 |

본문이 243바이트를 넘으면 `fmt.c`의 overflow 플래그가 서므로 마지막 3바이트를 `...`로 바꿔 잘렸음을 표시한다.

### 4.2 링버퍼

| 항목 | 값 |
|---|---|
| 칸 수 | `log_ring_kb * 1024 / 256`. 기본 16 KiB는 **64칸**, 허용 범위 4~1024 KiB(16~4096칸) |
| 메모리 | 초기화 때 `calloc`. 정적 배열로 잡지 않는다: 최댓값을 정적으로 잡으면 쓰지 않는 영역까지 `mlockall`로 고정되기 때문 |
| `head` | `atomic uint64`. 지금까지 쓴 줄 수. **생산자만 쓴다** |
| `tail` | `atomic uint64`. 지금까지 꺼낸 줄 수. **소비자만 쓴다** |
| `dropped` | `atomic uint64`. 버린 줄 수(§5.3) |
| 칸 번호 | `카운터 % 칸 수`. 64비트라 넘칠 일이 없다 |

판정은 모두 두 카운터의 차이로 한다.

- 사용 중인 칸 = `head - tail`
- 비었음: `head == tail`
- 가득 참: `head - tail == 칸 수`

## 5. 동기화 (단일 생산자, 단일 소비자, 락 없음)

### 5.1 원칙: 변수마다 쓰는 쪽을 하나로 한다

| 변수 | 쓰는 쪽 | 읽는 쪽 |
|---|---|---|
| `head`, 슬롯 내용 | 생산자 | 소비자 |
| `tail` | 소비자 | 생산자 |

한 변수를 두 스레드가 고치지 않으므로 서로 덮어쓰지 않는다. 락이 없어 메인 루프가 기록 스레드를 기다릴 일이 없다.

### 5.2 메모리 순서 (C11 `atomic`)

| 동작 | 순서 | 이유 |
|---|---|---|
| 생산자: 슬롯 내용 쓰기 → `head` 증가 | `head` 저장은 **release** | 슬롯 내용을 다 쓴 뒤에 "도착"이 보이도록 |
| 소비자: `head` 읽기 → 슬롯 읽기 | `head` 읽기는 **acquire** | "도착"을 본 뒤에는 슬롯 내용이 완성되어 있도록 |
| 소비자: 슬롯 다 읽기 → `tail` 증가 | `tail` 저장은 **release** | 다 읽은 칸만 생산자가 재사용하도록 |
| 생산자: `tail` 읽기 → 슬롯 쓰기 | `tail` 읽기는 **acquire** | 소비자가 읽기를 끝낸 칸만 덮어쓰도록 |

비유: 선반에 물건을 먼저 올리고 나서 "도착" 푯말을 올린다. 푯말을 먼저 올리면 수령인이 빈 선반을 가져간다.

### 5.3 가득 찼을 때: 새 로그를 버린다

생산자는 `reserve`에서 `head - tail == 칸 수`이면 **칸을 쓰지 않고** `dropped`를 1 올린 뒤 NULL을 돌려준다.
호출자는 NULL이면 줄 조립을 건너뛴다(조립 비용도 아낀다).

오래된 것을 덮어쓰는 방식을 쓰지 않는 이유: 소비자가 읽는 도중에 생산자가 같은 칸을 덮어써서 깨진 줄이 나가는 것을
막으려면 락이나 복잡한 재검증이 필요하다. 새 로그를 버리면 생산자는 소비자의 읽기를 전혀 신경 쓰지 않아도 된다.

`dropped`는 생산자가 올리고 소비자가 `exchange(0)`으로 읽어 가므로 두 스레드가 고친다. 단일 원자 연산이라 안전하며,
§5.1 원칙의 유일한 예외다. 소비자는 값이 0이 아니면 링버퍼를 거치지 않고 직접 `로그 N건 버림` 줄을 출력한다.

### 5.4 의사코드

```text
생산자:
  if !tg_log_begin(log, level, &b): return      // 가득 차면 dropped++ 하고 false
  ... b(슬롯의 text 244바이트)에 줄 조립 ...
  tg_log_end(log, &b)                           // len, ts_ns 기록
      head.store(head + 1, release)             // 먼저
      write(efd, 1)                             // 그 다음에

소비자:
  loop:
    read(efd)                                   // 카운터가 0이면 잠듦
    stopping = stop.load(acquire)               // 비우기 전에 먼저 읽는다 (§12)
    while tail != head.load(acquire):           // 카운터 값이 아니라 버퍼를 직접 확인
       슬롯을 모음 버퍼에 이어 붙임
       tail.store(tail + 1, release)
    모음 버퍼를 write
    n = dropped.exchange(0); if n: "N건 버림" 출력
    if stopping: break                          // 플래그를 본 뒤에 비웠으므로 그 이전의 줄과 버림이 모두 반영됐다
```

## 6. 깨우기: eventfd

`eventfd`는 커널이 들고 있는 64비트 카운터에 fd를 붙인 것이다.

| 호출 | 동작 |
|---|---|
| `write(efd, n)` | 카운터에 n을 더하고 잠든 스레드를 깨운다. 막히지 않는다 |
| `read(efd)` | 카운터 값을 돌려주고 0으로 되돌린다. 0이면 0이 아니게 될 때까지 잠든다 |

### 규칙 두 가지

1. **`head`를 올린 뒤에 `write(efd)`를 한다.** 순서가 반대면 소비자가 깨어나 빈 버퍼를 보고 다시 잠든 뒤에 `head`가
   올라가서, 다음 신호가 올 때까지 그 줄이 갇힌다.
2. **카운터 값을 줄 수로 믿지 않는다.** 깨어나면 항상 `tail != head`로 버퍼를 직접 확인해 빌 때까지 비운다.
   카운터는 "한 번 확인하라"는 신호일 뿐이다.

### 신호를 놓치지 않는 이유

카운터가 값을 쌓아 두므로, 소비자가 "비었다"고 판단한 직후에 생산자가 줄을 넣어도 다음 `read`가 즉시 반환한다.
반대로 신호가 불필요하게 한 번 더 와도(허위 깨어남) 소비자가 빈 버퍼를 확인하고 다시 잠들 뿐 해롭지 않다.

### 종료

정지 플래그(`atomic bool`)를 올리고 `write(efd)`로 깨운다. 소비자는 버퍼를 완전히 비운 뒤 끝나고, 메인은 `pthread_join`으로 기다린다.

### 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| 조건 변수 | mutex가 필수라 락이 다시 생긴다 |
| 파이프 | 내부 버퍼가 차면 `write`가 막히거나 실패한다 |
| 주기적 확인(예: 50~100 ms) | 한가할 때도 초당 10~20번 깨어난다 |
| futex 직접 사용 | 가능하나 수준이 낮아 실수하기 쉽다. eventfd가 glibc와 musl에서 모두 지원된다 |

## 7. 메인 루프용 API

줄을 슬롯 안에서 직접 조립해 복사를 한 번 줄인다.

```c
struct tg_log;                                   /* 링버퍼 + 스레드 + 출력 대상 */

int  tg_log_start(struct tg_log *l, const struct tg_config *cfg);
void tg_log_stop(struct tg_log *l);              /* 비운 뒤 스레드를 합치고 fd를 닫는다 */

/* 가득 차 있으면 false. true이면 b가 슬롯의 text 244바이트를 가리키도록 초기화된다. */
bool tg_log_begin(struct tg_log *l, enum tg_log_level lv, struct tg_buf *b);
void tg_log_end(struct tg_log *l, struct tg_buf *b);  /* 길이·시각 기록, head 증가, eventfd 신호 */
```

사용 예(개념):

```c
struct tg_buf b;
if (tg_log_begin(&log, TG_LOG_INFO, &b)) {
    tg_buf_str(&b, "judge kill cand=");
    tg_buf_str(&b, name);
    tg_buf_kv_u64(&b, "sys_avg_x100", d.sys_avg_x100);
    tg_log_end(&log, &b);
}
```

`printf` 계열은 쓰지 않는다. 기존 `fmt.c`(`tg_buf_*`)를 그대로 쓴다.

## 8. 출력 대상

기록 스레드는 출력 대상을 작은 인터페이스(`write` 함수 하나)로 감싸서 쓴다. 지금은 두 가지만 구현하고, 나중에 UDP 같은 대상을 추가해도 링버퍼와 스레드는 바꾸지 않는다.

| 설정 | 출력 |
|---|---|
| `log_path=`(비어 있음, 기본) | 표준 오류(fd 2). systemd 환경에서는 journald가 받는다 |
| `log_path=/절대/경로` | 그 파일. `O_WRONLY \| O_APPEND \| O_CREAT \| O_CLOEXEC`, 권한 0640 |

**지정한 `log_path`를 열 수 없으면**(디렉터리 없음, 권한 없음 등) 표준 오류로 대체하고, 그 사실을 알리는 경고 줄
(`log_path 열기 실패 errno=N, 표준 오류 사용`)을 첫 줄로 남긴다(§11). 로그 때문에 보호 기능이 꺼지지 않게 하려는 것이다.
경로의 형식이 잘못된 경우는 설정 검증 단계에서 이미 시작이 거부된다.

줄 형식은 기록 스레드가 만든다: `[<우선순위>]시각 레벨 본문` (예: `2026-11-11T15:04:05.123Z info judge kill ...`).
레벨 이름은 `err`, `warn`, `info`, `debug`다.

- 시각: 시작 때 한 번 `CLOCK_REALTIME`과 `CLOCK_MONOTONIC`을 함께 읽어 두고, 각 줄의 `ts_ns`를 실제 시각으로 환산한다.
  이 시각은 줄을 **쓴 시각**이지 파일에 적힌 시각이 아니다(지연되어도 사건 시각이 유지된다).
- 표준 오류가 journald를 거치는 환경(환경변수 `JOURNAL_STREAM` 존재)에서는 줄 앞에 `<3>`, `<4>`, `<6>`, `<7>`을 붙여 우선순위를 전달한다.

쓰기 처리:

- `EINTR`은 재시도한다. 일부만 쓰였으면(부분 쓰기) 나머지를 이어 쓴다.
- `EAGAIN`, `ENOSPC`, `EIO` 등 다른 실패는 해당 모음을 버리고 `write_errors`를 센다(숫자는 버림 줄과 함께 보고).
  기록 스레드가 쓰기 실패 때문에 멈추거나 무한 재시도하지 않는다.

## 9. 한계와 위험

| 항목 | 내용 |
|---|---|
| 강제 리셋 | `fsync`를 하지 않으므로 페이지 캐시에만 있던 마지막 줄들이 유실될 수 있다. 길벗 사건에서 로그를 남기지 못한 것과 같은 종류의 위험이다. 실험에서는 수집기(`tg-sampler`)처럼 UDP로 VM 밖에 보내는 출력 대상을 추가해 보완할 수 있다 |
| journald 지연 | journald도 일반 프로세스라 스래싱 중 느려지거나 멈출 수 있다. 그러면 기록 스레드의 `write`가 막히고, 링버퍼가 차서 새 로그가 버려진다. 메인 루프는 영향받지 않는다 |
| 부분 쓰기 뒤 실패 | 파일에 한 줄의 일부를 쓴 뒤 다음 `write`가 `ENOSPC` 등으로 실패하면, 모음은 버려지지만 이미 기록된 줄 조각은 남는다. 출력이 재개되면 다음 줄이 그 조각에 붙어 한 줄이 손상될 수 있다. 줄 경계를 복구하는 처리는 하지 않았다(디스크가 가득 찬 드문 상황) |
| 마지막 쓰기 실패 | 모음의 마지막 `write`가 실패하면 그 실패를 알릴 줄을 쓸 곳이 없고, 뒤이어 로그가 오지 않으면(특히 종료 직전) 쓰기 실패 횟수가 보고되지 않는다 |
| 최신 로그 손실 | 가득 차면 새 로그를 버리므로 가장 중요한 최신 사건이 사라질 수 있다. 버린 개수는 남으며, `log_ring_kb`를 키워 완화한다 |
| 단일 생산자 | 로그를 쓰는 스레드는 메인 루프 하나뿐이어야 한다. 스캔 스레드는 통계 숫자(atomic)만 남기고, 메인이 읽어 기록한다 |
| 락 없는 코드 | 틀리면 가끔씩만 나타나는 버그가 된다. §10의 반복 검증과 스레드 탐지기로 확인한다 |
| eventfd 비용 | 줄마다 시스템 콜 한 번이 추가된다. 마이크로초 단위로 알려져 있으나 **이 프로젝트에서 측정한 값은 없다.** 구현 후 잰다 |
| 스래싱 중 깨어남 지연 | 기록 스레드의 코드·스택이 쫓겨나면 깨어나는 데 오래 걸린다. `mlockall`로 완화한다(`selfprot`) |

## 10. 검증 계획

단위 테스트(ASan/UBSan, WSL):

| 항목 | 내용 |
|---|---|
| 순차 정확성 | 한 줄씩 쓰고 순서·내용이 같은지 |
| 가득 참 | 칸 수만큼 쓰면 다음 `begin`이 실패하고 `dropped`가 센다. 비운 뒤에는 다시 쓸 수 있다 |
| 버림 보고 | `N건 버림` 줄이 정확한 개수로 나간다 |
| 잘림 | 243바이트를 넘는 본문이 `...`로 잘린다 |
| 출력 대상 | 출력 인터페이스를 시험용으로 바꿔 끼워 내용을 수집한다. 쓰기 실패(`ENOSPC`)와 부분 쓰기를 주입한다 |
| 스트레스 | 생산자와 소비자를 수백만 줄 돌려, 버려지지 않은 모든 줄이 순서대로 깨지지 않고 도착하는지(번호 연속성)와 `쓴 줄 = 도착 + 버림`인지 확인한다. 소비자에 일부러 지연을 넣은 경우도 포함한다 |
| 신호 놓침 | 소비자가 "비었음"을 확인한 직후에 생산자가 쓰는 겹침을 지연 주입으로 재현해 줄이 갇히지 않는지 확인한다 |
| 종료 | 정지 요청 시점에 남은 줄이 모두 나가고 스레드가 합쳐진다 |
| 스레드 탐지기 | `-fsanitize=thread` 빌드를 별도 대상으로 돌려 데이터 경쟁이 없는지 확인한다 |

실측(구현 후, 숫자로 기록):

- 메인 루프의 한 줄 쓰기 비용(`begin`~`end`), 시스템 콜 포함
- 한가할 때 기록 스레드의 깨어남 횟수(0이어야 함)
- 링버퍼와 스레드가 추가하는 `VmRSS`·`VmLck`
- 초기화 이후 `malloc` 호출 수(M3-6의 `--wrap=malloc`으로 확인)

## 11. 확정한 세부 선택 (2026-11-11)

세 항목을 기본안과 대안의 장단점을 비교해 정했다. 1번은 처음 적은 기본안(시작 거부)에서 바꿨다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 지정한 `log_path` 파일을 열 수 없을 때 | **표준 오류로 대체하고 경고 줄을 남긴다** (처음 기본안은 시작 거부) | 설정 파일의 모르는 키를 거부하는 것은 오타가 안전장치를 조용히 끄기 때문이었다. 로그 경로 오류는 보호 기능에 영향이 없고, 실행 중 쓰기 실패도 줄을 버리고 계속 달리기로 했으므로 시작할 때만 죽는 것은 일관되지 않는다. 경로의 형식이 잘못된 경우(상대 경로 등)는 설정 검증이 시작을 거부한다 |
| 줄 크기 | **고정 256바이트** | 가득 참 판정과 칸 계산이 단순해 락 없는 구조의 검증이 쉽다. 효율 차이는 작다. 이벤트 루프를 붙인 뒤 줄이 자주 잘리면 512바이트로 키운다 |
| 쓰기 방식 | **4 KiB 버퍼에 모아 `write` 한 번** | 디스크가 막혔다 풀린 뒤 쌓인 줄을 빨리 따라잡아 링버퍼가 차는 것을 막는다. 쓰기 실패 시 손실은 한 번에 모은 최대 4 KiB로 한정된다(줄 수는 본문 길이에 따라 크게 달라지며 짧은 줄이면 수십 줄이다) |

실험에서 `log_path`로 데이터를 모으는 경우 대체가 일어나면 파일이 비어 있을 수 있다.
실험 스크립트는 시작 직후 로그 파일의 존재를 확인한다.

## 12. 구현 결과와 실측 (2026-11-11, WSL 6.18, VM 아님)

구현: `src/daemon/log.[ch]`, 테스트 `tests/test_log.c`(검사 4183개). 설계와 달라진 점은 없고, 구현 중 발견한 것은 아래와 같다.

### 구현 중 고친 버그

기록 스레드가 "비운 뒤에 정지 플래그를 읽는" 순서였다. 한 바퀴를 도는 사이 생산자가 마지막으로 줄을 버리고
정지를 요청하면, 그 버림 집계를 보고하지 못한 채 스레드가 끝날 수 있었다("쓴 줄 = 도착 + 버림"이 깨짐).
정지 플래그를 **먼저** 읽고 그 뒤에 한 번 더 비우도록 고쳤다. 생산자가 플래그를 올리기 전의 모든 줄과 버림이
그 비우기에 반영된다.

### 검증

| 항목 | 결과 |
|---|---|
| 단위 테스트(ASan/UBSan) | 통과. 같은 파일을 15회 반복 실행해 실패 0 |
| 스레드 탐지기(TSan, `make test-tsan`) | `test_log`, `test_targets`(스캔 스레드) 모두 데이터 경쟁 없음 |
| 스트레스 | 30만 줄을 크기 64칸 링버퍼에 밀어 넣어 도착 줄의 번호가 엄격히 증가하고 `도착 + 버림 = 쓴 줄`이 정확히 맞음. 느린 출력(호출당 50 µs)에서도 같음 |
| 줄이 갇히지 않음 | 드문드문 쓰는 3000줄에서 쉬는 지점마다 방금 쓴 줄이 도착함을 확인한다. 규칙 1(head 먼저, 그다음 깨우기)을 일부러 뒤집은 변이 코드는 20회 중 5회 이 테스트에서 실패했다. 경합이 드물게 걸려 매번 잡지는 못하지만 이 테스트가 해당 버그를 감지할 수 있음을 확인했다 |

TSan은 이 환경(WSL 6.18)의 주소 무작위화와 충돌해 `setarch -R`(프로세스 단위로 무작위화 끔)로 실행한다.
시스템 설정은 바꾸지 않았다.

### 실측

| 항목 | 값 | 조건 |
|---|---|---|
| 줄당 쓰기 비용 | 약 1.9 µs | `tg_log_begin` ~ `tg_log_end`(줄 조립, eventfd `write` 포함), 20만 줄 연속, 출력은 버림, WSL 4코어 |
| 유휴 시 기록 스레드 깨어남 | 3초 동안 0회 | 자발적 문맥 전환 횟수가 변하지 않음 |
| 깨어남 합치기 | 20만 줄에 약 1.4만 번 깨어남 | eventfd 카운터가 신호를 합치므로 줄마다 깨어나지 않음 |

이 비용은 연속으로 쏟아 부은 경우의 평균이다. 이벤트 루프의 실제 로그는 상태가 바뀔 때만 남기므로 훨씬 드물다.
VM에서의 값, 스래싱 중의 값, `VmRSS`·`VmLck`, 초기화 이후 `malloc` 호출 수(M3-6)는 아직 재지 못했다.
