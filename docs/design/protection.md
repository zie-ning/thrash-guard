# 보호 설계: 필수 프로세스와 데몬 자신

> 스래싱 중에도 **필수 프로세스(sshd 등)**와 **데몬 자신**이 살아서 응답하도록 하는 방법을 설명한다. 전체 흐름은 [overview.md](overview.md), 로그 구조는 [log-ringbuffer.md](log-ringbuffer.md)에 있다.
> 효과는 가설이며 [validation/overview.md](../validation/overview.md)에서 켬/끔으로 확인한다.

## 1. 한눈에 보기

"지킨다"는 두 가지를 막는 일이다.

| 겹 | 막으려는 일 |
|---|---|
| 종료 보호 | 프로세스가 종료되는 것 |
| 회수 보호 | 스래싱 중 메모리가 디스크로 쫓겨나 멈추는 것 |

종료 보호만 하면 죽지는 않지만 멈출 수 있고, 회수 보호만 하면 멈추지는 않지만 종료 대상이 될 수 있다. 목적에는 둘 다 필요하다. 지키는 대상은 둘이고 수단이 조금 다르다.

| 보호 대상 | 종료 보호 | 회수 보호 |
|---|---|---|
| 필수 프로세스 (sshd, 에이전트 등) | `oom_score_adj=-1000` | `memory.low` |
| 데몬 자신 | `oom_score_adj=-1000` (같음) | `mlockall` **+** `memory.low` |

데몬은 필수 프로세스가 받는 보호를 모두 받고, 거기에 `mlockall`을 더한다. 원칙은 **"프로그램 코드를 우리가 바꿀 수 있고 작으면 `mlockall`로 강하게, 남의 프로세스는 밖에서 설정으로 부드럽게"**다.

## 2. 필수 프로세스 보호

### 2.1 종료 보호: 하나의 기준을 커널과 공유

- 커널 OOM killer는 `oom_score_adj=-1000`인 프로세스를 절대 고르지 않는다.
- 데몬도 같은 기준을 쓴다. cgroup 안에 `oom_score_adj`가 `-1000`인 프로세스가 **하나라도** 있으면 그 cgroup을 종료 후보에서 제외한다.
  후보 스캔 스레드가 `cgroup.procs`와 `/proc/<pid>/oom_score_adj`를 읽어 판단하며, 핵심 경로 밖에서 수행한다.
- 그래서 사용자는 서비스 설정에 한 번만 적으면 `cgroup_kill`과 `oom_kill` 두 방식 모두에서 보호된다.

### 2.2 회수 보호: `memory.low`

`memory.low`는 "이 cgroup의 메모리는 가능한 한 회수하지 않는다"는 권고다. 한도 이하의 메모리는 다른 cgroup이 먼저 회수 대상이 된다.
회수할 곳이 정말 없으면 뚫릴 수 있다. 절대 회수하지 않는 `memory.min`은 잘못 잡으면 시스템 전체가 OOM으로 몰릴 수 있어 쓰지 않는다.

### 2.3 적용 방식: 설정 파일을 제공하고 데몬은 쓰지 않는다

- `packaging/`에 서비스별 systemd drop-in(`OOMScoreAdjust=-1000`, `MemoryLow=`)을 제공한다.
- 데몬은 다른 프로세스의 `oom_score_adj`나 `memory.low`를 **쓰지 않는다.** 스래싱 중에 남의 설정을 쓰다가 막힐 일이 없고, 서비스 재시작으로 pid가 바뀌어도 다시 적용할 필요가 없으며, 데몬의 권한과 위험이 작아진다.
- 기본 제공은 **데몬 자신과 `sshd`**다. 로그·관측 에이전트(journald, SSM Agent, CloudWatch Agent 등)는 환경마다 다르므로 예시와 작성 방법을 문서로 안내한다.
- `MemoryLow=` 크기는 서비스가 실제로 쓰는 메모리를 잰 뒤 정한다. 1 GiB 같은 작은 서버에서는 크게 잡을수록 다른 프로세스가 쓸 메모리를 깎는다.
- 검증 환경에서는 보호의 켬/끔을 독립 스위치로 두어 보호만의 효과를 분리해 본다.

### 2.4 한계

- **너무 많이 보호하면** 종료할 대상이 없어져 데몬이 개입하지 못한다. 작은 필수 서비스에만 쓰도록 문서에 경고한다.
- **한 cgroup에 필수와 문제 프로세스가 섞이면**(예: 로그인 세션 scope에 ssh 로그인과 메모리를 쓰는 프로세스) `cgroup_kill`은 그 cgroup을 건너뛴다. 프로세스 단위로 죽이는 `oom_kill`이 보완한다.
- 보호가 잘 되어 필수 프로세스가 계속 돌면 시스템 PSI `full`이 낮게 유지되어 워크로드만 스래싱하는 상황을 놓칠 수 있다(추론). 검증에서 확인한다.
- 데몬이 정상인데 큰 앱을 구분할 수는 없으므로, 지켜야 할 앱도 같은 방식으로 보호 설정을 한다.

## 3. 데몬 자기 보호

길벗 사건에서 먼저 멈춘 것은 SSM Agent, CloudWatch Agent, rsyslog 같은 관측 에이전트들이었다. 이 데몬은 같은 상황에서도 판단하고 종료할 수 있어야 한다.

### 3.1 요구와 방법

| 요구 | 방법 |
|---|---|
| 종료 대상 제외 | `OOMScoreAdjust=-1000` (2.1절과 같은 방식, 서비스 파일로 적용) |
| 메모리 회수 대상에서 제외 | `mlockall(MCL_CURRENT \| MCL_FUTURE)`, 스택 사전 접근, 스레드 스택 크기 고정(64 KiB), glibc arena 1개로 제한. 서비스 설정의 `MemoryLow=`를 함께 둔다 |
| 라이브러리 재적재 방지 | 정적 링크 |
| 핵심 경로의 할당 금지 | 초기화 때 모든 버퍼를 준비하고 이후 `malloc`을 쓰지 않는다 |
| docker 비의존 | Docker API 대신 `cgroup.kill`에 직접 쓰기 |
| 디스크 지연 격리 | 로그는 고정 링버퍼에 쌓고 별도 스레드가 기록한다 ([log-ringbuffer.md](log-ringbuffer.md)) |
| 디렉터리 읽기 지연 격리 | 후보 탐색은 별도 스레드가 맡는다 (3.3절) |

`mlockall`은 매핑된 영역을 전부 고정하므로 기본 스레드 스택(8 MiB)이 그대로 고정되면 메모리 목표(유휴 2 MiB 이하)를 넘는다. 그래서 스택 크기를 명시하고
링버퍼는 정적 배열이 아니라 초기화 때 필요한 만큼만 할당한다.

### 3.2 왜 데몬에는 `mlockall`을 더하나

| | `mlockall` | `memory.low` |
|---|---|---|
| 누가 적용하나 | **프로그램 자신**이 시작할 때 호출 | 프로그램 **밖**(systemd 설정)에서 cgroup에 설정 |
| 강도 | 강함. 고정한 페이지는 회수 대상에서 완전히 빠짐 | 약함. 권고라서 회수할 곳이 정말 없으면 뚫릴 수 있음 |
| 비용 | 고정한 만큼 **한가할 때도** 다른 프로세스가 못 씀 | 한도 이하만 보호하고 유연함 |
| 남의 프로세스에 | **불가능** (그 프로그램의 코드를 고쳐야 함) | 가능 |

1. **우리가 코드를 쥔 것은 데몬뿐이다.** `mlockall`은 프로그램이 자기 안에서 호출하는 함수라 sshd나 에이전트에는 쓸 수 없다. systemd에도 "이 서비스를 메모리에 고정하라"는 설정이 없다(`LimitMEMLOCK`은 한도만 정한다, 제 기억 기준). 남의 프로세스는 밖에서 걸 수 있는 `memory.low`가 유일한 수단이다.
2. **데몬은 가장 센 보호가 필요하다.** 스래싱의 최악 상황에서도 판단하고 종료해야 하는 데몬이 권고 수준의 보호에 기대면, 회수할 곳이 없어지는 바로 그 순간에 뚫릴 수 있다(추론).
3. **데몬은 작아서 `mlockall`의 비용이 작다.** 목표가 유휴 2 MiB 이하다. sshd와 에이전트를 전부 고정하면 수십~수백 MiB가 묶여 작은 서버에서는 다른 프로세스가 쓸 메모리를 깎는다.

선행 도구도 둘 다 쓴다. 조사한 범위에서 earlyoom은 `mlockall`(문서상 VmRSS 약 2 MiB)을 쓰고, oomd는 기본 꺼진 선택 기능 `--mlock-self`가 있으며 운영 문서에서는 자기 자신에 `MemoryMin/Low=64M`를 권고한다.

### 3.3 후보 스캔 구조

종료 후보는 `target_parent`의 직계 자식 cgroup이다. 디렉터리를 읽는 `readdir`는 스래싱 중에 막힐 수 있다. 메인 루프가 거기서 멈추면 감지 자체를 못 하므로 **스캔을 별도 스레드가 맡고
메인 루프는 완성된 표만 읽는다.**

- 후보 표는 고정 크기(32칸)이고, 칸마다 `memory.pressure`와 `memory.stat`의 fd를 열어 둔다. 판단 루프는 경로 탐색 없이 `pread`로 읽는다.
- 디렉터리는 `getdents64` 시스템 콜과 스택 버퍼로 읽어 **할당하지 않는다.**
- 표는 **이중 버퍼**다. 스캔 스레드가 현재 표가 아닌 쪽에 새 표를 만든 뒤 한 번의 원자적 교체로 공개하고, 메인은 표를 잡고 있는 동안에는 그 표를 건드리지 못하게 한다(그 회차의 스캔은 건너뜀). 락을 잡고 기다리는 쪽이 없다.
- 두 표는 같은 cgroup의 fd를 공유하므로 닫는 일은 한 곳에서만 한다. 사라진 cgroup의 fd는 두 표 어디에도 없을 때 닫는다.
- 컨테이너가 재시작되어 이름이 바뀌면 다음 스캔에서 새 항목으로 잡힌다. 새 항목은 `first_seen`을 기록해 시작 직후 유예에 쓴다. 데몬 시작 때 이미 있던 항목은 나이를 알 수 없어 유예를 면제한다.

### 3.4 검증 상태

| 항목 | 상태 |
|---|---|
| 스캔 스레드, 링버퍼 | 단위 테스트(ASan/UBSan)와 스레드 경쟁 검사(TSan) 통과 (WSL) |
| 줄당 로그 쓰기 비용, 유휴 시 기록 스레드 깨어남 | 약 1.9 µs, 3초 동안 0회 (WSL 실측) |
| 초기화 이후 `malloc` 0회 | 미검증 (테스트 빌드에서 `-Wl,--wrap=malloc`으로 세는 작업 예정) |
| `VmRSS`, `VmLck`, 스트레스 중 루프 지연 | 미측정 (이벤트 루프 구현 뒤 VM에서 측정) |

### 3.5 알려진 위험

- `/proc` 파일을 읽을 때 커널 내부에서 할당이 일어날 수 있어 완전한 무할당은 보장하지 못한다.
- `SCHED_FIFO` 같은 실시간 스케줄링은 효과와 시스템 영향을 측정한 뒤 적용 여부를 정한다.
- SIGKILL을 받은 희생자가 스래싱 때문에 종료를 못 하면 메모리가 풀리지 않을 수 있다(`process_mrelease` 같은 보조 수단은 후속 검토).
- 같은 이름으로 재생성된 cgroup의 열린 fd가 이전 cgroup을 가리킬 가능성(컨테이너 이름이 ID 기반이라 드물다고 보지만 미확인).

## 4. 미확인 (VM에서 확인)

- `memory.low`가 효과를 내려면 부모 slice에도 값이 필요한지, 필요하다면 systemd가 자동으로 전파하는지.
- `sshd`가 이미 자기 `oom_score_adj`를 `-1000`으로 두는지(그렇다면 sshd의 종료 보호는 이미 충족).
- 보호가 실제로 스래싱 중 SSH 응답을 유지하는지.
- 데몬에 `mlockall`과 `memory.low`를 함께 걸 때 `memory.low`가 추가로 효과가 있는지.
