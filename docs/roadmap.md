## 0. 계획 대비 보완점

계획을 작업으로 쪼개면서 발견한 빈틈과 그 대응이다.

| # | 빈틈 | 대응 |
|---|---|---|
| 1 | 스래싱 중에는 **수집기도 멈춘다**. 길벗에서 PSI를 못 남긴 이유와 같다. 수집기가 멈추면 H2를 판정할 수 없다. | 수집기 `tg-sampler`를 C로 먼저 만들고 데몬과 같은 자기 보호(mlockall, 정적 링크, 사전 할당)를 적용한다. 파서와 자기 보호 모듈은 데몬이 그대로 재사용한다. 자기 보호의 효과도 M0~M1에서 미리 검증된다. |
| 2 | Docker 컨테이너는 기본적으로 `system.slice` 아래에 생긴다. plan 4.3의 "`system.slice` 제외" 규칙과 충돌한다. | 실험용 컨테이너는 전용 `workload.slice` 아래에 둔다(`cgroup_parent`). 데몬과 systemd-oomd 모두 이 slice만 대상으로 삼는다. |
| 3 | 로컬 SSD는 EBS보다 훨씬 빠르다. VM에서는 재적재 비용이 작아 스래싱이 약하게 나타날 수 있다. | VM 디스크에 IOPS·대역폭 상한을 건다(gp3 기본값 3000 IOPS / 125 MiB/s에서 시작). 상한값은 실행 메타데이터에 기록한다. |
| 4 | 우리 데몬만 튜닝하고 systemd-oomd는 기본값(압력 지속 30초)으로 두면 비교가 불공정하다. | 기본값 구성 C2와, 지속 시간·임계를 맞춘 튜닝 구성 C2t를 함께 측정한다. |
| 5 | 6.8 계열 커널은 배포판 설정에 따라 MGLRU가 기본으로 켜져 있을 수 있다. 그렇다면 C0 자체가 "MGLRU on, `min_ttl_ms=0`"이다. | 모든 실행에서 `/sys/kernel/mm/lru_gen/enabled`와 `min_ttl_ms`를 기록한다. 길벗과 같은 AWS 커널의 기본값은 M6 전에 t3.micro에서 따로 확인한다. |
| 6 | "스래싱 시작"과 "복구"의 정의가 측정 가능한 형태가 아니다. | 2절에서 시점을 정의한다. |
| 7 | `mlockall(MCL_CURRENT)`은 매핑된 영역을 전부 고정한다. 기본 스레드 스택(8 MiB)과 glibc 스레드별 arena가 그대로 고정되면 2 MiB 목표를 넘는다. | 스레드 스택 크기를 명시하고(예: 64 KiB) `M_ARENA_MAX=1`로 둔다. 고정 메모리(`VmLck`)를 CI가 아닌 실기 측정 항목에 넣는다. |
| 8 | 판단 임계값을 실험 장비에서만 맞추면 반복이 느리다. | 판단 로직을 순수 함수로 분리한다. 그러면 M2에서 수집한 시계열을 오프라인으로 재생해 임계값을 평가할 수 있다(리플레이 테스트). |
| 9 | 커널 `min_ttl_ms`가 시스템 전체 스래싱을 충분히 막는다면, 데몬이 차별화될 곳이 불분명하다. 특히 `min_ttl_ms` 검사는 kswapd의 전역 회수 경로에 있는 것으로 보여, 컨테이너가 자기 상한(`memory.max`)에 걸린 내부 스래싱에서는 동작하지 않을 수 있다(가설). | 컨테이너 내부 스래싱(S2)을 M1에서 일찍 확인하고, M2 직후 방향 점검(M2-7)에서 데몬이 집중할 빈틈을 수치로 정한다. |

| D22 | S1 기준 조건(평가용 유도 조건) | anon 650 MiB(4 MiB/s), file 0, mlock 43 MiB, I/O 상한 100 IOPS로 확정한다. 이 조건의 재현율은 15회 중 9회 livelock(60%, 신뢰구간 약 33~83%)이다. 80% 목표에는 닿지 못했다. 시도한 레버(IOPS 150→100, anon 650/700, mlock 43 MiB, file 50 MiB) 중 재현율을 구분 가능하게 올린 것은 없었고, 3000 IOPS에서는 약 20회 모두 livelock이 나오지 않아 I/O 상한을 낮추는 것만 필수로 확인됐다. 이 조건은 길벗 관측값(143~147 IOPS)보다 느린 "평가용 유도 조건"이며 mlock 43 MiB는 길벗의 unevictable 관측값을 모사한 것이다. 가장 높은 값은 650 MiB·150 IOPS의 4/6(67%)이지만 표본이 작아 구분되지 않아 표본이 큰 조건을 택했다. 같은 조건에서 livelock과 OOM kill이 갈리는 이유는 미확인이다(가설: 회수 효율이 낮을수록 OOM kill으로 간다. 10회 중 일부 실행은 이 가설로 설명되지 않는다) | 확정 (2026-11-11) |

### D1. VM 플랫폼 비교

| | A. WSL 중첩 가상화 + QEMU/KVM | B. Multipass (Hyper-V) | C. Windows QEMU + WHPX |
|---|---|---|---|
| 준비 | `.wslconfig`에 `nestedVirtualization=true` 후 `wsl --shutdown`. CPU 지원 여부 확인 필요 | Multipass 설치 | QEMU for Windows 설치, Windows 하이퍼바이저 플랫폼 기능 활성화 |
| 디스크 I/O 상한 | QEMU `throttle-group`으로 스크립트에서 바로 설정 | 관리자 PowerShell `Set-VMHardDiskDrive -MaximumIOPS` | A와 같음(`throttle-group`) |
| 멈춘 VM 강제 리셋 | QMP `system_reset`, 스크립트로 자동화 쉬움 | `multipass restart`가 멈춘 VM에서 실패할 수 있어 Hyper-V 명령 필요 | A와 같음(QMP를 TCP로 열어 WSL에서 호출) |
| 스냅샷 | qcow2 백킹 파일로 매 실행마다 깨끗한 디스크 | Multipass 스냅샷(VM 정지 필요) | A와 같음 |
| 측정자 위치 | WSL(VM 밖)에서 bash로 전부 처리 | WSL↔Hyper-V 기본 스위치 간 네트워크 도달성이 환경마다 다름 | WSL. VM 포트는 Windows localhost로 전달되며 WSL에서 Windows 호스트로 접속한다 |
| 단점 | Docker Desktop도 WSL 재시작 영향을 받음. 중첩 가상화 성능 손실 | 자동화 경로가 Windows와 WSL로 나뉨 | WHPX 가속은 KVM보다 덜 쓰이는 경로라 안정성 확인 필요. 프로세스 관리가 Windows 쪽 |

**경과**: 처음에는 A를 골랐다. 그러나 `.wslconfig`에 `nestedVirtualization=true`를 넣고 재시작해도 WSL 커널에 `svm` 플래그와 `/dev/kvm`이 나타나지 않았다(Ryzen 5 7530U, Windows 11 26200, WSL 2.7.1). WSL은 "지원 안 함" 경고를 띄우지 않았고, Hyper-V Compute 로그에는 VM 생성 설정이 남지 않아 원인을 특정하지 못했다. Windows 보안 설정을 근거 없이 바꾸는 대신 C로 결정했다. C는 A의 자동화 장점(I/O 상한, QMP 리셋, qcow2 복원)을 유지한다. C도 막히면 B로 간다. 어느 쪽이든 VM 밖 측정자 = WSL이다.

**M0에서 알게 된 사실**

1. **MGLRU가 기본으로 켜져 있다.** 6.8 HWE 커널에서 `lru_gen/enabled=0x0007`, `min_ttl_ms=0`. 따라서 C0은 "MGLRU on, 보호 시간 0"이다. 길벗 AWS 커널의 기본값은 M6에서 확인한다.
2. **systemd-oomd는 기본 설치되어 있지 않다.** 22.04에서는 별도 패키지다. C2 측정(M2) 때 설치한다.
3. **stress-ng는 스래싱 재현에 부적합하다.** `--vm-bytes`를 퍼센트로 주든 절대값(380M × 2)으로 주든 익명 메모리를 약 430 MiB까지만 잡았고, 남은 메모리가 140~190 MiB로 유지되었다. 가용 메모리를 넘지 않도록 스스로 줄이는 것으로 보인다(미확인). M1의 재현 부하는 계획대로 직접 만든 `tg-load`로 한다.
4. **WHPX에서 게스트 재부팅이 실패한다.** 재부팅 순간 `WHPX: Unexpected VP exit code 4`로 VM이 일시정지된다. QEMU에 `-no-reboot`을 주고, 재시작은 "종료 후 새로 켜기"로 처리한다. QMP `system_reset`도 같은 문제를 겪을 수 있어 멈춘 VM은 강제 종료 후 새로 켠다.
5. **PSI avg10은 짧은 stall을 놓친다.** 위 실행에서 avg10 최대는 0.00%였지만 누적값 차분으로 계산한 250 ms 구간 stall은 4.3%였다. 분석과 데몬 판단은 `total` 차분을 기본으로 쓴다.
6. **SSH 새 연결 지연의 기준값은 약 200 ms다**(VM이 한가할 때). 복구 판정의 "1초 안에 성공" 기준은 이 값과 충분히 떨어져 있다.

| M2-1 | 구성 프로파일 `lab/profiles/`: C0, C3, C2(oomd 기본, `systemd-oomd` 설치 포함). 적용과 원복은 멱등. 서버 환경(swap, `mem_limit`)은 프로파일이 아니라 시나리오가 정한다(D11). oomd는 설치만으로는 `workload.slice`를 감시하지 않으므로 `ManagedOOMMemoryPressure=kill`을 설정하고 `oomctl`로 감시 대상을 확인한다(임계값은 기본값 유지). oomd 설치는 파일 내려받기이므로 이름·출처·크기를 알리고 확인을 받는다 |
| M2-2 | (선택) S2(swap 2 GiB + `swappiness=10` + `mem_limit`), S3(S2 환경에서 JVM 기동 버스트, 대량 파일 읽기) 시나리오 구현. S3 전체 대신 M2-5용 정상 부하 하나만 먼저 만든다 |
| M2-3 | 측정: 3개 구성(C0, C3, C2) × S1 × 5회. 부하는 모든 구성에서 `workload.slice` 안에서 돌리고(D20), C0도 새로 잰다. 하니스에 `--profile` 옵션, 부하의 slice 배치, 복구 시간(T_recover) 측정을 추가한다 |
| M2-4 | 분석 스크립트: 복구 시간 중앙값·범위, 미복구 비율, PSI 분포 그래프. 오탐 kill은 정상 부하(M2-5)에서 본다 |
| M2-5 | 보정: 정상 부하의 PSI 분포로 트리거·판단 임계 후보를 정한다. 반복 회차를 보정용과 평가용으로 나눈다 |
| M2-6 | 보고서 `docs/reports/M2-baseline.md`: "기존 방법으로 충분한가"에 대한 S1 한정 결론과 H4의 1차 판정(S1 한정), 성공 기준 재확정. H3(S2 필요)는 선택 과제를 할 때만 판정한다 |
| M2-7 | **방향 점검(축소)**: C2·C3가 S1에서 무엇을 막고 무엇을 놓치는지 정리하고 데몬이 집중할 부분을 정한다. 결정은 사용자와 함께 내리고 `docs/decisions/`에 기록한다 |

**선택 과제**: S2·S3 전체 구현, C2t(oomd 튜닝), 4개 구성 × S1~S3 전체 측정, H3 판정. 여력이 있거나 M2-7 결과가 필요로 할 때만 한다.

**완료 조건**: S1에서 C0·C3·C2의 복구 시간(또는 미복구 비율) 표가 채워지고, 임계 후보가 수치로 정해지며, M2-7 방향 점검 결과가 기록된다.

### M3. 데몬 MVP

> **핵심**: Thrash Guard의 최소 기능 버전을 만든다. 스래싱을 감지하면 원인 컨테이너를 종료하는 것까지가 범위다. 처음에는 판단만 기록하고 종료하지 않는 dry-run으로 오탐을 확인한다.

M1·M2 실험은 한 번에 수십 분이 걸린다. 실험이 도는 동안 M3-1~M3-3처럼 임계값과 무관한 부분은 WSL에서 먼저 개발해도 된다. 판단 임계값만 M2 이후에 넣는다.

| ID | 작업 |
|---|---|
| M3-1 | 설정 파서(`key=value`)와 CLI: `--config`, `--dry-run`(기본값 on), `--foreground` |
| M3-2 | 이벤트 루프: 시스템 PSI 트리거 등록, `poll(POLLPRI)`, 깨어난 지연 측정 |
| M3-3 | 대상 탐색 스레드: `workload.slice` 하위 cgroup을 미리 스캔해 고정 크기 표로 유지. 유예 시간, 쿨다운, 시간당 kill 상한 |
| M3-4 | 판단 v1(순수 함수): 트리거 후 N초 동안 PSI full 비율 ≥ X가 지속되면, 후보 중 `memory.pressure` full 증가량이 가장 큰 cgroup을 선택 |
| M3-5 | 종료 경로: `cgroup.kill` 쓰기, 링버퍼 로그 + 기록 스레드 |
| M3-6 | 무할당 검증: 테스트 빌드에서 `-Wl,--wrap=malloc`으로 초기화 이후 할당 횟수를 세어 0인지 확인 |
| M3-7 | 리플레이 테스트: M2 CSV를 판단 함수에 재생해 감지 시각과 오탐을 오프라인으로 계산 |
| M3-8 | `packaging/thrash-guard.service`: `OOMScoreAdjust=-1000` 등 |

**완료 조건**: VM S1에서 dry-run 판단 로그가 남고, dry-run을 끄면 실제 kill 후 복구된다. 유휴 시 `VmRSS`·`VmLck`와 스트레스 중 루프 지연을 기록한다.

### M4. MVP 평가

> **핵심**: 직접 만든 최소 기능 데몬이 재현한 문제를 실제로 해결하는지 같은 실험으로 확인한다. S1에서 데몬이 있을 때와 없을 때(C0)의 복구를 비교하고, 정상적인 바쁜 상황에서 엉뚱한 프로세스를 죽이지 않는지 본다. 결과에서 드러난 약점이 다음 개선(M5)의 근거가 된다(D17).

- C4 × S1 × 5회 측정. C0·C3·C2의 M2 결과와 비교한다. 복구 시간, 데몬 자원 사용량, 루프 지연을 함께 본다.
- 정상 부하(M2-5)에서 오탐 kill이 없는지 확인한다.
- H5의 1차 판정은 S1에서 내린다. S2·S3 확장은 M2의 선택 과제를 했을 때만 한다.
- (선택) C6(C4 + `min_ttl_ms=1000`)을 측정해, 커널 안전망과 함께 쓸 때 복구 시간·오탐이 어떻게 달라지는지 본다.
- **진행 판단**: M5에서 어떤 부분을 개선할지 약점을 근거로 정한다. 개선 여지가 없으면 그 결과를 보고서로 남긴다.

### M5. 개선 반복 (기능별 on/off 비교)

> **핵심**: M4에서 드러난 약점을 근거로 데몬을 개선한다. 감지를 더 정확하게(여러 지표를 함께 보기), 대응을 더 부드럽게(죽이기 전에 먼저 감속) 만드는 것이 후보다. 기능을 하나씩 켜고 끄며 각 기능이 실제로 효과가 있는지 따로 잰다. 기존 도구와 차별화하는 것이 목적이 아니라, 직접 만든 데몬을 근거를 가지고 개선하는 것이 목적이다(D17). 전부 만들 필요는 없고, 효과가 보이는 한두 개를 고른다.

| ID | 기능 | 확인할 효과 |
|---|---|---|
| F1 | 복합 판단: refault, `pgsteal/pgscan` 효율, `pswpin` | 정상 부하(M2-5) 오탐 감소 |
| F2 | 단계적 대응: `memory.high` 감속 → 개선 없으면 kill (감속은 별도 스레드) | kill 없이 복구되는 비율 |
| F3 | kill 직전 스냅샷: 대상 `memory.stat`, 프로세스 목록을 고정 버퍼에 보관 | 사후 분석 가능성 (정성 평가) |
| F4 | `oom_score_adj` 정리: 시스템 서비스는 낮게, `workload.slice`의 컨테이너는 높게 맞춰, 커널 OOM killer가 동작해도 컨테이너를 고르게 한다 | C6에서 커널 안전망이 엉뚱한 프로세스를 죽이는 비율 감소 |

각 기능은 하나씩 켜서 C4 대비 차이를 잰다(F4는 C6 대비이므로 C6을 측정했을 때만 한다). 고른 기능을 모두 켠 것이 C5다. M2-7 방향 점검과 M4 결과에 따라 기능의 우선순위를 다시 정한다.
