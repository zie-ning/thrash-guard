# 효과 검증 설계

> 데몬이 실제로 멈춘 시스템을 더 빨리 되살리고 필수 프로세스를 지키는지 어떻게 확인하는지 설명한다.
> 데몬 설계는 [design/overview.md](../design/overview.md), 용어와 측정 규칙은 [validation/measurement.md](measurement.md), 실험 환경은 [lab/environment.md](../lab/environment.md)에 있다. 값은 모두 임시 설계이며 본 실행 전이다.

## 1. 검증할 주장

| ID | 주장 |
|---|---|
| V1 | 스래싱 부하는 데몬 없이 접속 불가(SSH)와 PSI `full` 압력을 지속시키며, 그동안 OOM killer가 발동하지 않거나 늦다 (데몬 꺼짐 대용인 dry-run에서 확인하고, 재현되는 범위만 기록) |
| V2 | 데몬이 켜지면 스래싱이 더 빨리 해소된다 |
| V3 | 필수 프로세스 보호가 켜지면 스래싱 중에도 필수 프로세스가 응답한다 |
| V4 | 정상적인 버스트에서는 데몬이 종료를 결정하지 않는다 |
| V5 | 데몬이 부하 cgroup을 대상으로 고르고 보호된 필수 프로세스는 고르지 않는다 (관찰·기록하며 합격 여부에 쓰지 않는다) |

## 2. 방향: 직관적이고 단순하게

Facebook oomd 설계 글의 합성 테스트를 참고했다. 글에서 확인한 구조는 이렇다. 모든 앱을 최대 10 GB로 제한한 cgroup 하나에 넣고, 정상 워크로드(2 GB를 120초에 걸쳐 할당)가
오동작 프로세스와 경쟁하게 한다. 오동작 프로세스는 세 가지 패턴(`RUNAWAY_GROWTH` 천천히 누수, `BURST_MEM` 덩어리 할당·해제 반복, `SPIKE_MEM` 덩어리 할당 후 잠듦)으로 시험하고,
정상 워크로드의 벽시계 시간(완벽하면 120초)을 oomd와 커널 OOM killer에서 비교한다. 그림은 `BURST_MEM` 크기(1~4 GB)마다 두 조건의 막대를 나란히 놓은 모양이다.
오동작 프로세스의 개수, 속도, 다른 패턴의 결과는 글에서 확인하지 못했고 oomd 저장소에서 재현 코드도 찾지 못해(확인한 범위) 구조만 따르고 값은 직접 정했다.

| | Facebook 글 | 우리 |
|---|---|---|
| 구성 | 정상 워크로드 + 오동작 프로세스(패턴 3종) | 필수 프로세스 E + 부하 하나(폭주 2종과 정상 버스트) |
| 한도 | 10 GB cgroup | VM 전체 메모리(1 GiB), 디스크 처리량 약 10.9 MB/s. 한도를 따로 두지 않는다 |
| 비교 | oomd 대 커널 OOM killer | 데몬 켜짐 대 dry-run(꺼짐 대용) |
| 평가 | 정상 워크로드의 벽시계 시간 | 해소 시간(그래프)과 결과 중심의 합격 기준(5절) |

**정상 앱 W를 두지 않는 이유**: W는 합불에 쓰지 않고 종료 여부와 접근 지연만 기록하는 역할이었다. 합불 기준(E 응답, 해소 시간, 정상 버스트 무종료, 보호 프로세스 무종료)에는 필요하지 않아 뺐다.
대신 "정상 앱과 폭주 중 무엇을 고르는가"는 이 검증에서 확인하지 못한다(5절 V5 주의).

**부하 패턴**: 폭주는 `RUNAWAY_GROWTH`(천천히 계속 커짐)와 `SPIKE_MEM`(큰 메모리를 한 번에 잡고 계속 접근) 두 가지다. 둘은 증가 속도가 달라 감지 지연에 어떻게 영향을 주는지 볼 수 있다.
글의 `SPIKE_MEM`은 덩어리를 잡고 잠드는 동작이지만, 우리는 계속 접근하도록 바꿨다. swap이 없으면 익명 메모리는 어차피 회수되지 않으므로 접근 여부가 압력에 주는 영향은 작다고 보지만(가설, 미확인), 기존 스래싱 조건이 계속 접근하는 부하였다.
글의 `BURST_MEM`(덩어리 할당·해제 반복)은 폭주로 쓰지 않고 정상 버스트(오탐 확인용)로만 쓴다. 폭주로 맞춰 보았으나 이 환경에서는 `SPIKE_MEM`과 구별되는 지속 압력을 만들지 못했다(4절 예비 실행).

## 3. 환경과 구성 요소

환경은 1 GiB Linux VM(swap 없음, 디스크 **처리량 상한 약 10.9 MB/s**)이다. 이 상한은 길벗 장애 때 인스턴스의 EBS 기준 대역폭에 읽기가 묶였다는 조회 결과(다른 세션 전달, 직접 확인하지 않음)에서 가져왔고, IOPS가 아니라 처리량으로 제한한다(`docs/lab/environment.md` 5.6절). 배경으로 `mlock` 43 MiB를 고정해 길벗의 회수 불가 메모리를 모사한다(임시, `tg-load pin`).
아래 프로세스를 **각각 별도 cgroup**(systemd 서비스 `tg-canary`, `tg-load`)으로 실행한다. `cgroup.kill`은 cgroup 단위라 같은 cgroup 안에서는 구분할 수 없기 때문이다.
부하는 한 번에 하나만 E와 함께 돌린다. 한 실행은 E가 응답하는 기준 구간(15초)을 거친 뒤 부하를 투입한다.

| 역할 | 동작 | 보호 |
|---|---|---|
| **필수 프로세스 E** | 작은 응답 서버(카나리)와 VM 밖 SSH 프로브 | 함 (`oom_score_adj=-1000`) |
| `RUNAWAY_GROWTH` | `tg-load anon`. 익명 메모리를 초당 4 MiB로 650 MiB까지 늘리며 계속 접근 | 안 함 |
| `SPIKE_MEM` | `tg-load anon --rate-mib 0`. 650 MiB를 즉시 할당하고 계속 접근 | 안 함 |
| 정상 버스트 | `tg-load burst`. 400 MiB를 약 5초 유지하고 해제, 10초 쉬기를 반복하며 300초(20사이클) 관찰. 오탐 확인용 | 안 함 |

`RUNAWAY_GROWTH`의 650 MiB, 초당 4 MiB, `mlock` 43 MiB는 M3의 처리량 제한 조건에서 livelock을 만든 값이다(`results/m3/20261113/G_throughput_*`, `H_iopath_*`). 이전에 적었던 초당 10 MiB는 측정한 적이 없어 바꿨다.
E의 `MemoryLow`는 M3에서 효과가 없었고 선택 설정이라 쓰지 않는다.

**"할당"과 "점유"는 다르다.** 프로그램이 메모리를 요청해도 커널은 주소 공간만 약속하고, 실제 RAM은 그 페이지에 처음 쓰는 순간에 채워진다. 그래서 시험용 부하는 요청한 영역을 직접 써 주어야 점유되고, 유지하려면 이후에도 가끔 접근해야 한다.

**스래싱을 만드는 방식**: swap이 없으면 익명 메모리는 디스크로 내쫓을 곳이 없다. 예비 실행의 샘플 기록에서 `SPIKE_MEM`은 익명 메모리가 약 750 MiB, 가용 메모리 0, 파일 캐시 약 2 MiB가 되고 파일 refault가 초당 2천 건 안팎으로 계속 늘었다. 나머지 프로세스의 파일 페이지(코드 등)가 쫓겨났다 느린 디스크에서 다시 읽히며 멈춘다는 해석이다(관찰에서 나온 해석이며 원인을 따로 격리해 확인하지는 않았다). 그래서 별도의 파일 경쟁 부하 없이 익명 메모리 점유만으로 스래싱을 만든다.
파일을 `mmap`해 읽는 `FILE_THRASH` 부하는 `tg-load`에 구현돼 있지만 한 번도 실행하지 않았고 이번 검증에서는 쓰지 않는다.

## 4. 조건, 반복, 예비 실행

| 조건 | 내용 |
|---|---|
| 데몬 dry-run (꺼짐 대용) | 판단 로그만 남기고 종료하지 않는다. 시스템은 데몬이 없을 때와 같게 움직인다고 본다 |
| 데몬 켜짐 | 기본 `cgroup_kill`, 보호 적용. 후보 유예 등은 기본값(30초) 그대로 |

폭주 2종(`RUNAWAY_GROWTH`, `SPIKE_MEM`) × 2조건 × 3회 = 12회, 정상 버스트는 dry-run 3회로 모두 15회다. 정상 버스트는 종료 결정이 있었는지를 판단 로그로 확인하면 충분해 켜짐을 돌리지 않는다.
한 실행의 시간은 스모크에서 잰 값으로 어림한다. dry-run은 부하가 스스로 끝나(600초) VM이 돌아온 뒤 로그를 가져오므로 약 13분(1회 실측), 켜짐은 약 5분(1회 실측), 정상 버스트는 약 7분(관찰 300초 포함, 예비 실행 기준)이다. 모두 합쳐 2시간 남짓이다(추정).

**dry-run을 꺼짐 대용으로 쓰는 가정**: M3의 dry-run 기록에서 커널 OOM killer의 개입 없이 livelock이 5분 넘게 이어진 것을 관찰했지만, 데몬 없는 실행과 직접 비교하지는 않았다. 이 가정은 한계로 보고서에 적는다.
dry-run의 가상 종료도 시간당 상한을 소모하므로(M3 H 기록) 판단 로그에서는 첫 결정 시각만 쓴다.

**예비 실행(보정용, 2026-11-13)**: 본 실행 전에 부하 크기를 맞췄다. 모두 dry-run이고, 부하마다 3회를 상한으로 했다. 원본은 `results/m4/prelim/`이며 본 실행의 평가에는 쓰지 않는다. 각 1회씩의 관찰이다.

| 부하 | 값 | 결과 | 결정 |
|---|---|---|---|
| `SPIKE_MEM` | 650 MiB 즉시 | T0 6.0초(SSH), 데몬 첫 결정 33.0초(유예), 커널 OOM 1건이 부하 시작 후 약 104초에 풀어 해소 시간 98.2초, E 카나리 최대 무응답 85.1초 | 확정 |
| 정상 버스트 | 300 MiB | 압력이 낮음(1초 최대 3.8%, 10초 평균 최대 0.6%, 가용 최저 178 MiB), SSH 실패 없음 | 시험으로 약해 제외 |
| 정상 버스트 | 400 MiB, 20사이클 | 1초 최대 49.9%, 10초 평균 최대 40.1%, 가용 최저 76 MiB, SSH 불가 구간이 있었고(T0 3.1초, 해소 11.0초) 종료 결정 0건 | 확정 |
| `BURST_MEM` | 500 MiB(유지 20초, 쉬기 10초와 5초) | 압력이 할당 직후에만 오르고 유지 중에는 calm이라 약 20초에 해소 | 제외 |
| `BURST_MEM` | 650 MiB(유지 20초, 쉬기 5초) | 첫 할당 중 파일 refault가 계속 늘어 스래싱이었고 SSH가 6.0초부터 막혔지만 23.7초에 커널 OOM이 부하를 종료해 해소 시간 24.2초(데몬 유예 전). 처음 기준(메모리 `full` 10%가 3초 연속)으로는 T0를 못 잡았다 | 제외 |

정상 버스트 400 MiB의 첫 시도는 하네스가 첫 사이클에서 끝내 오탐 여부를 볼 수 없어 무효였고, 관찰 시간 전체를 보도록 고친 뒤 다시 했다. 400 MiB가 유효한 시험인 이유는 10초 평균 `full`이 데몬 임계(10%)를 훨씬 넘었는데도 데몬이 가용 메모리 조건(`mem_available`)으로 걸러냈기 때문이다.
`BURST_MEM`은 500 MiB에서는 지속 압력이 없고 650 MiB에서는 커널 OOM이 먼저 끝내, `SPIKE_MEM`과 구별되는 부하가 되지 못해 폭주 목록에서 뺐다. 그 사이의 크기(550~600 MiB)는 상한을 넘겨 시도하지 않았다.

**스래싱이 나지 않은 경우**: dry-run에서 T0가 나오지 않거나 커널 OOM kill로 끝나면 그대로 기록한다. 그 부하의 V2는 "판정 불가"로 적고 다른 부하의 결과는 그대로 쓴다.
T0(SSH 3번 연속 실패)는 정지를 관찰하는 기준일 뿐 데몬의 종료 임계(`full_pct`, 초기값 10%)와는 별개다([measurement.md](measurement.md) 1절). 종료 임계에 못 미쳐 데몬이 반응하지 않는 부하는 데몬의 실패가 아니라 부하 선정의 문제로 기록하고 부하를 조정한다.

후속(2단계)으로 보호 끔 같은 다른 구성, `memory.min` 소량 선택 시험, 데몬 `mlock` 대조군(이슈 #6)을 둔다.

## 5. 합격 기준

**합격은 결과로 판단한다. 부하만 죽여야 한다는 조건을 두지 않는다.** 데몬은 프로세스의 의도를 알 수 없고 선택은 [design/overview.md](../design/overview.md) 3절의 규칙을 따를 뿐이며,
목적은 "멈춘 시스템을 빨리 되살리고 필수 프로세스를 지키는 것"이기 때문이다.

| 구분 | 지표 | 합격 기준 (데몬 켜짐, 임시) |
|---|---|---|
| 합불 | 필수 프로세스 E(카나리) | 종료되지 않고, T0부터 해소까지 카나리의 최대 무응답 시간이 5초 이내이며 dry-run 이하(dry-run에서도 무응답이 없으면 동률로 합격, dry-run보다 줄었는지는 기록). SSH 프로브의 같은 값은 보조로 기록한다 |
| 합불 | 해소 시간 | dry-run보다 짧고 60초 이내(T0와 해소는 SSH 프로브 기준, [measurement.md](measurement.md) 1절). 종료해도 T0 이후 5분 안에 해소되지 않으면 실패 |
| 합불 | 정상 버스트 | 정상 버스트 dry-run 3회의 판단 로그에 종료 결정이 한 번도 없음 (있으면 오탐) |
| 합불 | 보호된 프로세스 | 종료 0건 |
| 기록 | 종료된 대상과 역할 | 합불에 쓰지 않음. 대상이 부하 cgroup이고 E가 아닌지 점검하는 용도 |
| 기록 | 데몬 선행 비율 | 합불에 쓰지 않음. 해소가 데몬의 종료 때문인지 커널 OOM killer 때문인지(`judge kill` 로그와 `dmesg`)를 매 실행 기록하고 비율을 낸다. dry-run에서 커널이 해소하는 데 걸리는 시간 분포도 함께 본다 |

dry-run 대조군이 5분 안에 풀리지 않으면 "미해소(5분 이상)"로만 표시하고 실제 해소 시간은 알 수 없다.

**결과 표현**: Facebook 글의 그림과 같은 모양으로 그린다. 가로축은 부하(`RUNAWAY_GROWTH`, `SPIKE_MEM`), 세로축은 해소 시간이고, 부하마다 dry-run과 켜짐 막대를 나란히 놓는다. 막대는 중앙값, 선은 3회의 최소~최대 범위다.
5분 안에 풀리지 않은 실행은 상한에 "미해소"로 표시한다. 정상 버스트는 그래프가 아니라 종료 결정 횟수 표로 보고한다.

**후보 유예와 감지 지연**: 데몬은 새로 발견한 후보 cgroup을 30초 동안 종료 대상에서 뺀다(막 시작해 커지는 정상 앱을 지키려는 안전 여유값, `startup_grace_sec`). 이 값은 바꾸지 않고 기본값 그대로 측정한다.
`RUNAWAY_GROWTH`는 스래싱이 약 150초 뒤에 시작해 유예와 무관하다. 반면 `SPIKE_MEM`은 시작 약 6초에 SSH가 막히지만 데몬의 첫 결정이 약 33초(예비 실행)로 유예에 묶이므로, 켜짐의 해소 시간이 데몬의 판단 속도가 아니라 유예에 지배된다. 보고서에 이 사실을 명시한다.

**V5 해석 주의**: 이 구성에서는 후보가 부하 하나뿐이라 선택 규칙(증가량·크기 우선)이 정상과 폭주를 구별하는지는 확인하지 않는다. 확인하는 것은 부하가 있을 때 데몬이 그것을 종료하고 시스템이 해소되는지, 보호된 E가 대상에서 빠지는지다.
정상 앱을 잘못 고르는 경우는 보호 설정으로 해결하는 것이 원칙이며, 이 한계를 보고서에 명시한다(보호된 cgroup 제외는 M3에서 확인했다).

## 6. 위험

| 위험 | 대응 |
|---|---|
| `SPIKE_MEM`의 결과가 같은 조건에서도 갈림(커널 OOM 시점이 들쭉날쭉) | 예비 실행에서 T0와 약 68초 뒤 커널 OOM 해소를 1회 확인했다. M1에서도 같은 조건에서 livelock과 OOM kill이 갈렸으므로 3회 결과를 범위로 보고한다 |
| 부하가 dry-run에서 T0를 만들지 못함 | "스래싱 미발생"으로 기록하고 판정 불가로 표기. 부하 조정은 예비 실행에서만 한다 |
| T0를 PSI로 재면 정지 시작보다 늦거나 놓침 | 처음 기준(메모리 `full` 10%가 3초 연속)은 `SPIKE_MEM`에서 정지 시작(약 6초)보다 30초 늦은 36.3초에, `BURST_MEM` 650 MiB에서는 아예 못 잡았다. 압력이 1초 단위로 요동쳤기 때문이며, 굳어진 정지에서 메모리 `full`이 낮고 io `full`이 지배한다는 M3 관찰과 같은 현상일 수 있다(추정, io PSI는 기록하지 않았다). **T0와 해소를 SSH 프로브 기준으로 바꾸고** PSI(10초 평균)는 보조 기록과 어긋남 표시로 남겼다. 연속 횟수(3번, 5번)는 예비 실행 10개를 보고 정한 임시값이라 본 실행에서 다시 확인한다 |
| T0와 해소가 SSH 한 신호에 의존 | SSH는 카나리보다 스래싱에 민감해 "접속 불가 구간"을 재는 것이다(스모크에서 SSH 14초, 카나리 1.5초). 3번 연속 실패로 호스트 쪽 일시 지연을 거르고, E 합격은 카나리로 따로 판정하며, PSI 보조 기록과 어긋나는 실행을 표시한다 |
| 후보 유예 30초가 `SPIKE_MEM`의 감지 지연을 지배 | 기본값 그대로 측정하고 보고서에 명시한다. 감도 비교는 후속 |
| dry-run이 꺼짐과 같다는 가정이 틀림 | 한계로 명시한다. 후속에서 데몬 없는 실행과 직접 비교 |
| 필수 프로세스 보호로 시스템 `full`이 낮게 유지되어 놓침 | 검증에서 확인, 놓치면 대상 구역 `full` 신호를 추가 |
| 합성 부하와 실제 앱의 차이 | 결과를 "합성 부하에서의 값"으로만 표현 |
| 임계값 과적합 | 보정에 쓴 실행과 평가 실행을 구분 |
| 굳어진 livelock에서 memory full 규칙이 늦게 반응 | 처리량 제한 조건에서 3회 중 2회가 67~147초 뒤에야 충족. io 경로를 구현했고(overview.md 4절) 기록 재생에서 19~24초로 줄었다. 정상 버스트와 `SPIKE_MEM`으로 io 경로의 오탐과 동작을 M4에서 확인 |
| 디스크 조건이 실제와 다름 | 처리량 상한은 일정한 상한이고 실제 EBS의 크레딧 소진 과정과 네트워크 지연은 모사하지 않는다. 결과를 "처리량 상한 모사 조건에서의 값"으로만 표현하고, 실제 인스턴스는 후속에서 확인 |
| 5분 상한이 dry-run의 실제 해소 시간을 가림 | "미해소(5분 이상)"로만 표시하고 그 이상은 주장하지 않는다 |
| `BURST_MEM`(반복 할당·해제)을 폭주로 검증하지 못함 | 한계로 명시한다. 후속에서 550~600 MiB 같은 중간 크기를 시도할 수 있다 |

## 7. 후속 확장

기존 도구와의 비교(systemd-oomd, earlyoom), swap이 있는 환경, 메모리 크기·커널 버전·실행 형태 조합, 실제 클라우드 인스턴스 측정, MGLRU `min_ttl_ms`와의 조합, 파일 경쟁 부하(`FILE_THRASH`), 정상 앱 W를 함께 두는 구성, 폭주형 `BURST_MEM`(중간 크기), 후보 유예를 줄인 조건의 감도 비교.
결과는 "합성 부하를 쓴 VM 실험에서의 값"이며 "데몬 꺼짐 대비"로만 말하고, 기존 도구보다 낫다는 주장은 하지 않는다.
