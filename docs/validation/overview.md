# 효과 검증 설계

> 데몬이 실제로 멈춘 시스템을 더 빨리 되살리고 필수 프로세스를 지키는지 어떻게 확인하는지 설명한다.
> 데몬 설계는 [design/overview.md](../design/overview.md), 용어와 측정 규칙은 [validation/measurement.md](measurement.md), 실험 환경은 [lab/environment.md](../lab/environment.md)에 있다. 값은 모두 임시 설계이며 측정 전이다.

## 1. 검증할 주장

| ID | 주장 |
|---|---|
| V1 | 스래싱 부하는 데몬 없이 PSI `full`을 지속시키며, 그동안 OOM killer가 발동하지 않거나 늦다 (재현되는 범위만 기록) |
| V2 | 데몬이 켜지면 스래싱이 더 빨리 해소된다 |
| V3 | 필수 프로세스 보호가 켜지면 스래싱 중에도 필수 프로세스가 응답한다 |
| V4 | 정상적인 버스트에서는 데몬이 아무것도 종료하지 않는다 |
| V5 | 데몬이 문서화한 선택 규칙에 따라 대상을 고른다 (관찰·기록하며 합격 여부에 쓰지 않는다) |

## 2. 방향: 직관적이고 단순하게

Facebook oomd 설계 글의 합성 테스트를 참고했다. 글에서 확인한 구조는 이렇다. 모든 앱을 메모리를 제한한 cgroup 하나에 넣고, 정상 워크로드(2GB를 120초에 걸쳐 할당)와
성격이 다른 폭주 프로세스 세 종류(`RUNAWAY_GROWTH` 천천히 누수, `BURST_MEM` 덩어리 할당·해제 반복, `SPIKE_MEM` 덩어리 할당 후 잠듦)를 경쟁시키고,
정상 워크로드의 벽시계 시간(완벽하면 120초)으로 평가한다. 폭주 프로세스의 크기·속도, 비교 조건, 그래프별 결과는 확인하지 못했고 oomd 저장소에서 재현 코드도 찾지 못해(확인한 범위) 구조만 따르고 값은 직접 정했다.

| | Facebook 글 | 우리 |
|---|---|---|
| 정상 일꾼 하나 + 폭주 프로세스, 한 번에 하나씩 | 폭주 3종 | 폭주 2종 (`RUNAWAY_GROWTH`, `FILE_THRASH`) |
| 정상 워크로드 | 2GB를 120초에 걸쳐 할당 | 워밍업 뒤 변동이 적은 정상 상태를 유지 |
| 한도 | cgroup의 `memory.max` | VM 전체 메모리(1 GiB). 한도를 따로 두지 않는다 |
| 평가 | 정상 워크로드의 벽시계 시간 | 결과 중심의 합격 기준(5절) |
| 추가 | | 필수 프로세스 E, 정상 버스트(오탐 확인), 데몬 꺼짐/켜짐 비교 |

**폭주 프로세스를 2종으로 줄인 이유**: 폭주는 "계속 커져서 시스템을 멈추는 것"만 둔다. Facebook 글의 `BURST_MEM`(덩어리 할당·해제 반복)은 아래 정상 버스트와 동작이 같아 정상 버스트로 합쳤고,
`SPIKE_MEM`(덩어리를 한 번 잡고 유지)은 계속 커지지 않아 폭주로 보기 어렵고 swap이 없으면 스래싱보다 OOM kill로 끝나기 쉬워(추정) 뺐다.
정상 앱도 120초에 걸쳐 할당하는 정의는 느린 누수와 곡선이 같아 데몬이 구분할 근거가 없었다. 실무의 정상 서비스는 워밍업 뒤 메모리 변동이 작다고 가정해(가설, 미확인) 정상 상태 유지로 바꿨다.

## 3. 환경과 구성 요소

환경은 1 GiB Linux VM(swap 없음, 디스크 I/O 상한)이다. 아래 프로세스를 **각각 별도 cgroup**(예: `systemd-run`의 scope)으로 실행한다. `cgroup.kill`은 cgroup 단위라 같은 cgroup 안에서는 구분할 수 없기 때문이다.
폭주 프로세스는 한 번에 하나씩 W, E와 함께 돌리며, W가 정상 상태에 들어간 뒤에 투입한다(잘 돌던 시스템에 문제가 생기는 순서).

| 역할 | 동작 (임시 값) | 보호 |
|---|---|---|
| **정상 앱 W** | 처음 20~30초 동안 약 200 MiB 작업집합을 채우는 워밍업을 한 뒤, 실행이 끝날 때까지 ±2% 안팎으로만 변동하며 작업집합을 일정 주기로 읽는다(접근 지연을 기록) | 안 함 |
| **필수 프로세스 E** | 작은 응답 서버(카나리)와 VM 밖 SSH 프로브 | 함 (`oom_score_adj=-1000`, `MemoryLow`) |
| `RUNAWAY_GROWTH` | 일정 속도(약 10 MiB/s)로 계속 할당하고 해제하지 않음 | 안 함 |
| `FILE_THRASH` | 익명 메모리를 RAM 거의 끝까지 채운 뒤, 남은 메모리보다 큰 파일을 `mmap`해 무작위로 계속 읽음 | 안 함 |
| 정상 버스트 | 큰 덩어리(약 300 MiB)를 할당해 몇 초 유지, 해제, 잠깐 쉬고 주기적으로 반복 (오탐 확인용) | 안 함 |

**"할당"과 "점유"는 다르다.** 프로그램이 메모리를 요청해도 커널은 주소 공간만 약속하고, 실제 RAM은 그 페이지에 처음 쓰는 순간에 채워진다. 그래서 시험용 부하는 요청한 영역을 직접 써 주어야 점유되고, 유지하려면 이후에도 가끔 접근해야 한다.

**`FILE_THRASH`이 필요한 이유**: swap이 없으면 익명 메모리는 디스크로 내쫓을 곳이 없다. 익명 메모리만 늘리면 스래싱이 아니라 곧바로 커널 OOM kill이 난다(M0에서 `stress-ng`가 부적합했던 이유도 같다).
스래싱은 파일 작업집합이 경쟁해 같은 페이지를 쫓아냈다 다시 읽는 상태에서 생긴다.

## 4. 조건, 반복, 최소 재현 탐색

| 단계 | 조건 |
|---|---|
| 1단계 | 데몬 **꺼짐** vs 데몬 **켜짐**(기본 `cgroup_kill`, 보호 적용). 켜짐도 먼저 dry-run으로 판단 로그만 확인해 임계값과 선택 규칙을 점검한다 |
| 2단계 (후속) | 보호 끔 등 다른 구성 |

폭주 2종(`RUNAWAY_GROWTH`, `FILE_THRASH`) × 2조건 × 3회 = 12회, 정상 버스트 3회로 모두 15회다. 1회 5분 안팎으로 보면 1시간 반 안팎이다(추정, 실측 아님).

**최소 재현 탐색**: `FILE_THRASH`이 "PSI `full`이 10% 이상으로 수십 초 지속되고 그동안 OOM kill이 없는" 상태를 만드는지 찾는다. 길벗처럼 10분짜리 livelock을 만들 필요는 없다. 다만 10%는 스래싱을 관찰하는 기준일 뿐 데몬의 종료 임계(`full_pct`, 초기값 40%)와는 별개다([measurement.md](measurement.md) 1절).
따라서 효과 비교에 쓸 부하는 관찰 기준에 더해 데몬의 설정된 종료 조건도 데몬 켜짐에서 충족하는지 따로 확인한다. 종료 임계에 못 미쳐 데몬이 반응하지 않는 부하는 데몬의 실패가 아니라 부하 선정의 문제로 기록하고 부하를 조정한다.
시간 상자는 하루 이내, 소수의 시도를 제안한다(미확정). 못 찾으면 재현 범위와 사유를 기록한 뒤 `RUNAWAY_GROWTH`만으로 검증한다. 탐색 순서: 디스크 I/O 상한 강화, 파일 비율 증가, 증가 속도 감소.

## 5. 합격 기준

**합격은 결과로 판단한다. 폭주 프로세스만 죽여야 한다는 조건을 두지 않는다.** 데몬은 프로세스의 의도를 알 수 없고 선택은 [design/overview.md](../design/overview.md) 3절의 규칙을 따를 뿐이며,
목적은 "멈춘 시스템을 빨리 되살리고 필수 프로세스를 지키는 것"이기 때문이다.

| 구분 | 지표 | 합격 기준 (데몬 켜짐, 임시) |
|---|---|---|
| 합불 | 필수 프로세스 E | 종료되지 않고, 스래싱 중 최대 무응답 시간이 5초 이내이며 꺼짐 이하(꺼짐에서도 무응답이 없으면 동률로 합격, 꺼짐보다 줄었는지는 기록) |
| 합불 | 해소 시간 | 꺼짐보다 짧고 60초 이내. 아무것도 종료하지 않아 해소되지 않으면 실패 |
| 합불 | 정상 버스트 | 아무것도 종료하지 않음 |
| 합불 | 보호된 프로세스 | 종료 0건 |
| 기록 | 종료된 대상과 역할 | 합불에 쓰지 않음. 선택 규칙이 의도대로 동작했는지 점검하는 용도 |
| 기록 | W의 종료 여부와 접근 지연(p50, p99) | 합불에 쓰지 않음 |
| 기록 | 데몬 비용 | `VmRSS`, `VmLck`, CPU, 루프 지연 |

W가 선택되어 종료될 수도 있다. W는 정상 상태에서 늘지 않으므로 증가량 우선 규칙상 폭주보다 뒤로 밀린다고 기대하지만(가설), 합불에는 영향을 주지 않고 기록에 남겨 선택 규칙을 점검한다. W를 지켜야 한다면 W도 보호 설정으로 지정한다.

**V5 해석 주의**: 이 구성에서 폭주 프로세스는 W보다 크고 W가 안정된 뒤에 투입되므로, 데몬이 폭주를 골랐더라도 "의도를 구별했다"가 아니라 증가량·크기 규칙을 따른 결과일 가능성이 높다.
이 검증이 확인하는 것은 큰 폭주가 있을 때 데몬이 그것을 종료하고 시스템이 해소되는지이며, 정상과 폭주를 구별하는 능력은 확인하지 않는다.

## 6. 위험

| 위험 | 대응 |
|---|---|
| `FILE_THRASH`이 재현되지 않고 OOM kill로 끝남 | 시간 상자를 두고 탐색, 못 찾으면 범위를 기록하고 `RUNAWAY_GROWTH`만으로 검증 |
| 크기·증가량 기준이 큰 정상 앱을 고름 | 보호 설정으로 해결하는 것이 원칙, 한계를 문서에 명시하고 후보별 지표를 기록해 점검 |
| 필수 프로세스 보호로 시스템 `full`이 낮게 유지되어 놓침 | 검증에서 확인, 놓치면 대상 구역 `full` 신호를 추가 |
| 합성 부하와 실제 앱의 차이 | 결과를 "합성 부하에서의 값"으로만 표현 |
| 임계값 과적합 | 보정에 쓴 실행과 평가 실행을 구분 |

## 7. 후속 확장

기존 도구와의 비교(systemd-oomd, earlyoom), swap이 있는 환경, 메모리 크기·커널 버전·실행 형태 조합, 실제 클라우드 인스턴스 측정, MGLRU `min_ttl_ms`와의 조합.
결과는 "합성 부하를 쓴 VM 실험에서의 값"이며 "데몬 꺼짐 대비"로만 말하고, 기존 도구보다 낫다는 주장은 하지 않는다.
