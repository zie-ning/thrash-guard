# 실험 계획: 데몬 `mlockall` 대조군 (이슈 #6)

> 스래싱 중 데몬이 틱 지연 없이 판단·종료한 것이 `mlockall` 덕분인지 확인한다. 이 문서는 실행 전에 쓴 계획이다. 결과는 아래 "결과" 절과 `design/protection.md` 3.4절에 있다. 측정 원본(실행별 로그, 14열 기록)은 저장소 지침에 따라 커밋하지 않고 로컬(`results/m3/20261114/`)에만 둔다.

## 질문과 가설

1. 스래싱 중 데몬의 틱 지연과 판단 로그 공백이 `mlock`을 끄면 늘어나는가?
2. 늘어난다면 원인이 데몬 페이지의 회수와 재적재인가? (데몬의 major page fault 수로 확인)

가설(미확인): 데몬은 대부분 `poll`로 자고 있어 페이지가 차가워진다. `mlock`을 끄면 그 페이지가 회수 대상이 되고, 스래싱 중 깨어날 때 느린 디스크에서 다시 읽어야 해서 틱이 늦어진다. 반대로 데몬이 작아서(`VmRSS` 약 1.4 MiB) 회수되지 않을 수도 있다.

## 설계

비교하는 것은 `mlock` 설정 하나다. 나머지는 모두 같게 둔다.

| 항목 | 값 |
|---|---|
| 팔 | A: `mlock = true`(기본), B: `mlock = false`(설정 파일) |
| 횟수 | **팔당 5회**, A1 B1 A2 B2 … 순서로 번갈아 실행 |
| 디스크 | 처리량 약 10.9 MB/s 제한, IOPS 3000 (`results/m3/20261113/G_throughput_*`와 같은 조건) |
| 부하 | 단일 hog(650 MiB를 초당 4 MiB로 증가), 도커 밖 `tg-load pin` 43 MiB |
| 데몬 | 서비스 실행, dry-run |
| 로그 | 두 팔 모두 `log_path`를 `/dev/shm` 파일로 둔다. journald가 느려져 생기는 공백이 데몬 지연으로 읽히는 것을 막기 위해서다 |
| VM | 1 GiB, 2 vCPU, swap 없음. 매 실행마다 새로 시작 |

실행 스크립트는 `runC_throughput.sh`(원본 `results/m3/20261113/scripts/`)를 바탕으로 `mlock` 인자와 로그 경로만 추가한다.

## 측정

- 데몬 통계: `late_ticks`, `max_delay_ms`, `sample_errors`
- 판단 로그 타임스탬프 간격(정지 구간의 공백 길이)
- 데몬 프로세스의 `minflt`, `majflt`(`/proc/<pid>/stat`), `VmRSS`, `VmLck`(`/proc/<pid>/status`): 1초 간격. 실행마다 PID가 달라 `psirec`이 PID를 인자로 받는다.
- 적용 확인: 실행 직후 `VmLck`를 기록한다. A는 0보다 크고 B는 0이어야 하며, 어긋난 회는 결과에서 제외하고 이유를 적는다.
- 보조: 로그인 불가 구간, 배너 응답(정지 구간 정렬용)

## 판정 기준 (실행 전에 정함)

기준선은 지난 관측(23회, 틱 11,757회)의 최대 지연 15 ms, `late_ticks` 0이다.

> **사후 보완**: 실행 전에 정한 [측정] 행은 B 팔만 기준선과 비교했다. 표의 "A의 `max_delay_ms`가 기준선 부근(수십 ms 미만)"이라는 조건은 **실행과 결과 정리가 끝난 뒤 PR 리뷰를 받아 추가한 것**이다("수십 ms 미만"의 경계도 이때 정했다). 실제 A 팔 결과(2~22 ms)는 이 조건에 들지만, 결과를 보고 정한 조건임을 밝혀 둔다.

| 결과 | 서술 |
|---|---|
| A의 `max_delay_ms`가 기준선 부근(수십 ms 미만)이고, B의 `max_delay_ms`가 기준선을 넘어 수십 ms 이상 늘고, B의 데몬 `majflt`가 증가 | "`mlockall`이 스래싱 중 틱 지연을 막았다"를 **[측정]** 으로 서술 |
| 두 팔이 비슷(B도 기준선 범위 안, `majflt` 증가 없음) | "이 조건에서 `mlockall`의 기여는 입증하지 못했다. 데몬이 작아서 회수되지 않았을 가능성"으로 서술하고 주장을 낮춘다 |
| 지연은 늘었는데 `majflt`는 증가하지 않음 | 원인이 페이지 회수가 아닐 수 있다. 질문 2는 입증하지 못한 것으로 쓰고 따로 조사한다 |
| B에서 오히려 지연이 적음 | 원인을 따로 조사한다 |

livelock이 나지 않은 회는 제외하고 횟수를 따로 적는다.

## 한계

- 팔당 5회라 작은 차이는 구분하지 못한다. 정지 시간이 회마다 크게 다르다.
- VM 한 종류(1 GiB, 2 vCPU)이고 정지는 최장 약 5분이다. 길벗 장애는 27시간이었다.
- `mlock=false`여도 스레드 스택 사전 접근 등 다른 자기 보호는 그대로다.
- 소요 시간은 G 실험 한 회 약 7분 기준 추정(미확인)으로, 10회에 1시간 반~2시간 안팎이다.

## 작업 순서

1. `lab/collect/psirec.c`에 데몬 PID 열(`minflt`, `majflt`, `VmRSS`, `VmLck`) 추가
2. 실행 스크립트 작성(`mlock`·로그 경로 인자, 적용 확인)
3. A·B 번갈아 5쌍 실행
4. 결과 표를 이 문서에 정리(원본은 로컬에만 보관)
5. `docs/design/protection.md` 검증 상태표의 "스트레스 중 루프 지연" 행에 결과 추가

## 결과 (2026-11-14 실행)

### 실행 조건 (모든 회 같음)

Ubuntu 22.04, 커널 6.8.0-138, 메모리 1 GiB, 2 vCPU, swap 없음, 디스크 **처리량 10.9 MB/s 제한**·IOPS 3000(이전 처리량 제한 실험(G)과 같은 조건), 도커 컨테이너 안 hog(`tg-load anon` 650 MiB, 초당 4 MiB, 420초), 도커 밖 `tg-load pin` 43 MiB, 데몬은 서비스로 실행하는 dry-run, 판단 설정은 기본값, 로그는 `/dev/shm/tg.log`(journald를 거치지 않음). 매 회 VM을 새로 시작했다.

- 모든 회에서 `sample_errors=0`, `kill_errors=0`, 실제 종료 0회(dry-run)다.
- "로그인 불가 시도 수"는 10초 간격 SSH 시도 중 배너 교환이 시간 초과된 횟수다. 두 팔 모두 18~23회로, 시스템 정지의 길이는 비슷하다(데몬이 정지를 풀지 않는 dry-run이므로 당연하다).
- `VmLck`는 데몬 시작 직후 읽은 값이고, 설정이 적용됐는지 확인하는 용도다. 어긋난 회는 없었다.

### 읽을 때 주의

- 5회씩이고 mlock 팔은 유효 4회다. 통계 검정으로 읽지 않는다. 다만 두 팔이 겹치지 않는다(`late_ticks` 0 대 71~120, `max_delay_ms` 최대 22 ms 대 최소 5,600 ms).
- mlock 팔의 `max_delay_ms`는 2~22 ms로, 지난 관측의 15 ms 기준선을 조금 넘는 회가 있다(수십 ms 미만이라는 계획의 조건에는 든다).
- `psi.tsv`의 마지막 몇 줄은 데몬을 멈춘 뒤라 데몬 열이 0이다. 집계에서 뺐다. `majflt`는 누적값이라 최댓값에서 첫 값을 뺐다.
- 판단 로그의 타임스탬프 공백은 지표로 쓰지 않았다. 데몬은 틱마다가 아니라 트리거·판단 시점에만 로그를 남기므로 mlock 팔에서도 1~2분 공백이 생겨(86~148초) 틱 지연을 반영하지 못한다. 틱 지연은 `late_ticks`와 `max_delay_ms`로 본다.
- 실행 스크립트로 먼저 돌린 `nomlock` 시험 1회(`late_ticks=20`, `max_delay_ms=240750`, `majflt` 2,463)는 이 표에 넣지 않았다. 설정 조회 권한 오류를 고치기 전 실행이라 원본을 저장소에 두지 않았다.
- 이 기록은 길벗 장애 재현이 아니다. VM 한 종류, 정지 약 5분(길벗은 27시간)이다.
