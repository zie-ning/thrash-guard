# 측정 정의와 규칙

> 효과 검증에서 쓰는 용어와 측정 규칙을 정한다. 검증 설계는 [validation/overview.md](overview.md)에 있다. 값은 모두 임시이며 본 실행 전이다.

## 1. 용어

| 용어 | 정의 |
|---|---|
| T0 (정지 시작) | VM 밖 SSH 프로브(1초 간격, 새 연결)가 **3번 연속 실패**한 첫 프로브의 시작 시각. "서버에 접속할 수 없게 된 시점"이다 |
| T_detect | 데몬이 "스래싱 지속"으로 판단한 시각(판단 로그) |
| T_kill | 종료가 실행된 시각(`cgroup.kill` 쓰기 또는 커널 OOM killer 호출) |
| T_resolve (해소) | T0 이후 SSH 프로브가 **5번 연속 성공**한 시점(5번째 성공의 완료 시각). 실행 초기에 성공했던 프로브는 쓰지 않는다. 데몬 꺼짐에서 부하가 자연 종료되거나 커널 OOM killer가 발동해도 같은 정의로 판단한다. 단 부하의 자체 종료(`--duration`)로 창이 잘리면 해소로 세지 않고 truncated로 기록한다 |
| 해소 시간 | T_resolve − T0. 구성은 아래 1.2절 |
| 미해소 | T0 + 5분까지 T_resolve가 없음. 이후 실행을 종료하고 정리한다. dry-run의 미해소는 "5분 이상"으로만 표시한다 |
| 오탐 | 정상 버스트 실행에서 데몬이 종료를 결정한 것(판단 로그의 `judge kill`, dry-run의 가상 종료 포함). 한 번이라도 있으면 오탐이고 정상 버스트의 합격 기준이다. 정상 버스트는 압력이 높아 T0가 나올 수 있으므로 T0 유무는 따지지 않는다 |
| 필수 프로세스 응답 | VM 밖에서 1초마다 필수 프로세스 E(카나리)에 TCP 요청(제한 시간 1초). T0부터 해소까지의 최대 무응답 시간과 성공률을 기록한다. 합불에는 쓰지 않는다([overview.md](overview.md) 5절). SSH 프로브의 같은 값도 보조로 기록한다 |
| 기준 구간 | 실행 시작 후 E가 응답하는 15초. 이 구간이 끝나면 부하를 투입한다 |
| 종료된 대상 | 종료된 cgroup 이름과 역할(부하, E, 기타) |

연속 횟수(3번, 5번)는 임시값이다. 프로브는 시작 시각 순으로 늘어놓고 연속을 센다(멈춘 동안에는 프로브가 겹쳐 돌 수 있다). 호스트 쪽의 일시적 지연이 실패 한 번으로 보이는 것을 거르려고 3번 연속을 요구한다.

**왜 SSH인가**: 효과 검증이 알고 싶은 것은 "멈춘 시스템이 되살아나는가"이고, 접속 가능 여부가 그 결과를 직접 보여 준다. 길벗 장애에서도 SSH가 먼저 멈췄다. 데몬이 보는 신호(PSI)와 따로 VM 밖에서 재므로, 데몬 판단과 같은 신호로 정의가 순환하지 않는다.
SSH(새 연결, `fork`, 로그인)는 필수 프로세스 E의 카나리보다 스래싱에 훨씬 민감하다(스모크에서 같은 정지에 SSH는 14초, 카나리는 1.5초 늦음). 그래서 T0와 해소는 "SSH 불가 구간"을 재는 것이고 "모든 서비스가 멈춘 시점"이 아니다.

### 1.1 보조 기록: PSI 기준의 같은 값

판정에는 쓰지 않고, SSH 기준과 어긋나는지 보는 용도로 분석 결과에 함께 남긴다.

| 항목 | 정의 |
|---|---|
| PSI T0 | 시스템 PSI `full`의 1초 구간 비율의 10초 평균이 10% 이상인 첫 창 안에서, 처음 10% 이상인 구간의 시작 |
| PSI 해소 | PSI T0 이후 비율이 10% 미만인 구간이 10초 연속된 구간의 끝 |
| 어긋남 | 한쪽만 T0가 있거나, 둘 다 있는데 10초 넘게 차이가 남 |

PSI 비율은 누적값 `total`의 차분으로 계산한다(`avg10`은 짧은 stall을 놓친다). 10%는 관찰 기준이고 데몬의 종료 임계(`full_pct`, 초기값 10%)와는 별개다.
처음에는 "10% 이상이 3초 연속"을 T0로 삼았으나, 굳어진 정지에서는 1초 구간 비율이 요동쳐(`SPIKE_MEM`은 43%, 66% 뒤에 1~7%와 20~40%를 오감) 정지 시작보다 30초 늦거나(`SPIKE_MEM`) 아예 못 잡았다(`BURST_MEM` 650 MiB). 10초 평균으로 바꾸면 SSH 기준과 같은 시각에 잡혔다. 이 기준은 예비 실행 10개를 보고 고른 것이라 본 실행에서 다시 확인한다.

### 1.2 해소 시간의 구성

데몬 켜짐에서 해소 시간은 세 구간으로 나뉜다.

```text
T0 ──────► T_detect ──► T_kill ──────► T_resolve
 접속       데몬이       종료 실행      접속 회복
 불가       결정                        확인
 (감지 지연)            (종료 후 회복 지연)
```

- 감지 지연: T0부터 T_detect까지. 첫 판단에 10초 윈도가 차야 해서 최소 10초 안팎이다. 새로 생긴 후보 cgroup에는 30초 유예가 있어, 스래싱이 부하 시작 직후에 일어나면(`SPIKE_MEM`) 유예가 감지 지연을 지배한다. 유예는 기본값 그대로 두고 측정한다.
- 종료 후 회복 지연: T_kill부터 T_resolve까지. 종료한 프로세스가 디스크 읽기를 기다리느라 SIGKILL 처리가 늦을 수 있고, sshd가 필요한 파일을 다시 읽어야 접속이 돌아오며, 성공이 5번 연속되어야 해소로 본다.

데몬 dry-run에서는 종료가 없으므로 해소 시간은 커널 OOM killer나 부하 자체의 종료로 풀린 시간이다. 5분 안에 풀리지 않으면 미해소다.

SSH 프로브는 연결 재사용(ControlMaster)을 쓰지 않는다. 재사용하면 sshd의 `fork`·로그인 경로를 건너뛰어 실제 접속 가능 여부를 반영하지 못하기 때문이다. 프로브는 멈춘 동안에도 1초마다 새로 시작해 최대 5~6개가 겹치므로 VM에 부하를 조금 더하지만, dry-run과 켜짐에 똑같이 적용된다.

## 2. 시각과 수집

- 시각은 모두 VM 밖 수신기의 시계로 맞춘다. 샘플러는 자체 단조 시계도 함께 보내 전송 지연을 확인한다.
- 데몬 로그의 시각은 VM 벽시계라, 실행 시작과 끝에 잰 VM 시계 차이(guest − host)를 빼서 수신기 시계로 맞춘다. 예비 실행에서 11분 동안 0.27초 어긋났다.
- 샘플러 `tg-sampler`는 250 ms 주기로 PSI·vmstat·meminfo를 읽어 UDP 텍스트 한 줄씩(일련번호 포함) VM 밖 수신기에 보낸다. 디스크 쓰기를 핵심 경로에서 빼고, 강제 리셋 때 기록이 유실되지 않게 하려는 것이다. 샘플러는 메모리 PSI만 기록하고 io PSI는 기록하지 않는다.

## 3. 측정 규칙

- 측정자는 반드시 대상 호스트 밖에 둔다(VM 밖 SSH 프로브, UDP 수집기).
- 시나리오·조건별 3회 이상 반복하고 중앙값과 범위를 보고한다.
- `T0` 이후 5분 안에 해소되지 않으면 "미해소"로 기록하고 정리한다. 부하를 시작한 지 10분 안에 `T0`가 나타나지 않으면 "스래싱 미발생"으로 기록하고 종료한다(임시).
- dry-run의 판단 로그는 첫 결정 시각만 `T_detect`로 쓴다. dry-run의 가상 종료도 시간당 상한을 소모하므로 첫 결정 이후의 `hourly_limit`, `no_candidate` 건너뜀은 해석하지 않는다.
- 부하 크기는 예비 실행(보정용)으로 맞췄다(`results/m4/prelim/`). 보정에 쓴 실행은 평가 실행과 구분해 기록하고 평가에 쓰지 않는다.
- 정상 버스트는 T0나 해소와 무관하게 관찰 시간(300초) 전체를 본다. 데몬의 후보 유예 때문에 첫 사이클에서 끝내면 오탐 여부를 알 수 없다.
- 수신기에서 일련번호가 건너뛴 구간은 무효로 기록한다. 무효 구간이 겹치는 1초 구간은 PSI 보조 기록에서 쓰지 않고, 무효 구간이 든 10초 창도 판정하지 않는다. UDP는 전달을 보장하지 않기 때문이다. 분석기가 일련번호를 읽어 처리한다.
- 원본 데이터는 `results/`에 커밋해 재검증할 수 있게 한다.
- 표본 부족 등 해석의 한계를 결과와 함께 적고, 실측과 추론을 구분한다.
- 임계값 보정에 쓴 실행과 평가에 쓴 실행을 구분한다.
