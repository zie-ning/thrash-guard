# Thrash Guard 프로젝트 계획

> 상태: 개발 중 (2026-11-12에 목적을 재정의했다). 수치는 모두 측정 전 가설이다. 이 문서는 "무엇을, 왜"만 다루고, 설계·검증·환경 문서는 [문서 안내](README.md)에서 찾는다.

Thrash Guard는 메모리 압박(스래싱)으로 시스템이 사실상 멈췄는데도 커널 OOM killer가 발동하지 않는 상황에서,
**OOM killer를 기다리지 않고 더 빨리 메모리 압박의 원인을 종료해 시스템을 되살리는 범용 데몬**이다. 스래싱 중에도 필수 프로세스(sshd 등)는 지킨다.

## 배경

커널 OOM killer는 메모리를 할당하다가 회수에 완전히 실패했을 때 발동한다. 스래싱은 같은 페이지를 쫓아냈다가 디스크에서 다시 읽기를 반복하는 상태라
느리게나마 계속 진척이 있어서, 커널은 "아직 회수하고 있다"고 보고 OOM killer를 부르지 않는다(추론). 그 사이 시스템은 응답하지 않고 사람이 재부팅할 때까지 길게 지속될 수 있다.

동기가 된 사례는 팀 캡스톤 프로젝트 "길벗"의 운영 EC2(t3.micro)가 2026-07-15~16에 약 27시간 응답 불능에 빠진 장애다. 가용 메모리가 0~11 MiB를 오갔지만 커널 OOM killer는
한 번도 발동하지 않았고, SSM Agent, CloudWatch Agent, rsyslog 같은 데몬이 먼저 멈춰 수동 재부팅으로 끝났다. 분석 결론은 리클레임 스래싱 livelock이지만 PSI 등을 확보하지 못해 메커니즘은
**간접 추론**으로 남아 있다. 길벗은 이 프로젝트의 **동기**이지 검증 대상이 아니다.

- [EC2 응답 불능 문제 해결하기](https://github.com/kookmin-sw/2026-capstone-26/blob/930b40aa2a42dd0923ee06d277151f0f9ddf826c/backend/docs/tech/infra/EC2%20응답%20불능%20문제%20해결하기.md)

비슷한 유저스페이스 도구(Facebook oomd, systemd-oomd, earlyoom, nohang)가 있다. 공통점은 **감지는 압력·여유량, 희생자 선택은 크기**라는 점이며 이 프로젝트도 이를 따른다.
조사 기록은 [reports/related-work.md](reports/related-work.md)에 있다.

## 목적과 범위

| 기둥 | 내용 |
|---|---|
| ① 더 빨리 해소 | 멈춤을 감지하면 비보호 대상을 직접 종료한다 |
| ② 필수 프로세스 보호 | sshd 등은 스래싱 중에도 응답하고 종료 대상에서도 제외된다 |
| ③ 범용 | 특정 서버에 한정하지 않는다. cgroup v2 + PSI가 있는 리눅스면 컨테이너 유무와 상관없다 |

목표는 스래싱 "제거"가 아니라 "지속 시간과 피해 범위의 제한"이다. 작업집합이 RAM보다 크면 어떤 설정으로도 스래싱 자체를 없앨 수 없다.

**비목표**: 커널 수정, 길벗 운영 서버 적용(효과를 주장하지 않음), 다중 노드 오케스트레이션, 범용 메모리 관리 대체.
**후속 과제로 미룸**: 기존 도구(systemd-oomd, earlyoom 등)와의 비교, swap이 있는 환경의 검증, 환경 조합 확장, 실제 클라우드 인스턴스 측정.

## 결과 서술 원칙

- 성과는 "합성 부하를 쓴 VM 실험에서의 결과"로 표현하고 운영 적용 효과처럼 쓰지 않는다. 측정 전에는 수치를 쓰지 않는다.
- 길벗 장애 분석에서 출발했다는 맥락은 링크로 잇고, 길벗 자료를 옮길 때는 호스트명·인스턴스 ID를 제거한다. 팀 프로젝트 자료이므로 원문은 링크를 우선한다.
