# Thrash Guard

메모리가 부족해 서버가 멈췄는데도 커널이 프로세스를 종료하지 않는 상태를 감지하고, 커널보다 먼저 원인 프로세스를 종료하는 리눅스 유저스페이스 데몬이다.

## 문제: 리클레임 스래싱 (livelock)

리눅스는 메모리가 부족해지면 OOM Killer로 프로세스를 종료해 메모리를 확보한다. 그런데 swap이 없는 서버에서는 OOM Killer가 발동하지 않은 채 시스템이 무기한 멈추는 상태(리클레임 스래싱 livelock)가 생길 수 있다. 원리는 다음과 같다.

1. swap이 없으면 프로세스가 쓰는 익명 메모리는 내보낼 곳이 없다. 커널이 회수할 수 있는 것은 디스크에 원본이 있는 페이지 캐시 뿐이다.
2. 커널은 메모리가 부족해도 페이지를 조금이라도 회수하는 데 성공하면 OOM Killer를 발동하지 않고 회수를 다시 시도한다. 새 메모리를 요구하는 프로세스가 계속 있으면 커널은 계속 조금씩 회수에 성공하므로 OOM Killer가 발동할 조건에 닿지 않는다.
3. 쫓겨난 페이지에는 실행 중인 프로세스의 코드와 라이브러리도 포함된다. 프로세스는 이 페이지가 필요해지는 순간 멈추고 디스크에서 다시 읽어 오며, 읽어 오면 다른 페이지가 다시 쫓겨난다.
4. 결과적으로 시스템은 새 일을 하지 못하고 페이지를 내보내고 다시 읽는 일만 반복한다. 디스크는 읽기로 포화되고, 모든 프로세스가 페이지를 기다리며 멈춘다. sshd 같은 필수 프로세스도 예외가 아니어서 접속조차 되지 않는다.
5. 이 반복은 스스로 끝나지 않는다. 메모리를 풀어 줄 유일한 방법은 원인 프로세스의 종료인데, 커널은 아직 회수에 성공하고 있다고 보아 종료하지 않고, 종료를 맡길 프로세스도 멈춰 있다.

그래서 커널이 개입하기를 기다리지 않고, 사용자 공간에서 이 상태를 감지해 원인 프로세스를 먼저 종료하는 데몬을 만들었다. 이 상황을 로컬 VM(메모리 1GB, swap 없음)에서 재현했고, 5분 동안 OOM Killer가 발동하지 않는 것을 5회 모두에서 확인했다. 자세한 재현 과정은 [portfolio/README.md](portfolio/README.md)에 있다.

## 동작 방식

1. **탐지:** PSI(Pressure Stall Information) 트리거로 평소에는 `poll`로 잠들어 있다가, memory PSI가 1초 중 15%를 넘기면 깨어난다. 이후 250 ms마다 PSI와 가용 메모리를 읽어 최근 10초 평균으로 판단한다.

   | 경로 | 조건 |
   |---|---|
   | memory 경로 | memory PSI 10초 평균 10% 이상 + 가용 메모리 10% 이하 |
   | io 경로 | IO PSI 10초 평균 50% 이상 + 가용 메모리 5% 이하 |

2. **선택:** cgroup 단위로 최근 10초 동안 메모리가 가장 많이 늘어난 후보를 먼저 고른다. 늘어난 것이 없으면 사용량이 가장 큰 것을 고른다. 전체 메모리의 10%도 쓰지 않는 후보는 뺀다.
3. **종료:** 선택한 cgroup의 `cgroup.kill`에 `1`을 쓴다(리눅스 5.14 이상). 쓰기 한 번에 커널이 그룹의 모든 프로세스를 종료한다.
4. **보호:** systemd 설정에 `OOMScoreAdjust=-1000`이 있는 서비스는 종료 후보에서 뺀다. 데몬 자신도 같은 설정을 걸고, `mlockall`로 메모리를 고정하고, 초기화 후에는 메모리를 할당하지 않는다. 판단하는 메인 스레드는 스캔과 로그 쓰기를 다른 스레드에 맡겨 스래싱 중에도 기다리지 않는다.

설계 문서는 [docs/design/](docs/design/)에 있다.

## 검증 결과

1 GiB VM(swap 없음, 디스크 처리량 약 10.9 MB/s 제한)에서 확인했다. 자세한 내용은 [docs/reports/M4-validation.md](docs/reports/M4-validation.md)에 있다.

- **메모리 누수(초당 4 MiB씩 증가):** 데몬을 켜면 시스템이 멈춘 뒤 18.2~23.2초에 풀렸다. 종료하지 않는 dry-run에서는 3회 모두 5분 안에 풀리지 않았다.
- **메모리 급증(650 MiB 한 번에):** 데몬이 7.3~12.7초에 풀었다. 커널 OOM Killer도 7~11초에 개입해 차이는 작았고, 커널이 먼저 종료하는 경우도 있었다.
- **정상 버스트(400 MiB를 5초 쓰고 10초 쉼, 20회):** 데몬도 커널도 종료하지 않았다. 가용 메모리가 66~83 MiB 남아 종료 조건이 충족되지 않았다.


## 구성 요소

| 경로 | 내용 |
|---|---|
| `src/common/` | `/proc`·cgroup 파서, 자기 보호, 할당 없는 문자열 조립 (수집기·데몬 공용) |
| `src/sampler/` | `tg-sampler`: 스래싱 중에도 버티도록 메모리를 고정하고, 지표를 UDP로 VM 밖에 보내는 수집기 |
| `src/daemon/` | `thrash-guard` 데몬: 설정, 안전장치, 후보 탐색, 판단, 로그, 이벤트 루프, 종료 경로 |
| `packaging/` | 서비스 파일, 설정 예시, sshd 보호 설정 예시 |
| `lab/` | 실험용 VM, 부하 실행, 수집기와 분석 스크립트 |
| `tests/` | 단위 테스트와 실제 커널에서 캡처한 `/proc` fixture |
| `portfolio/` | 프로젝트 소개 문서 |

문서는 [docs/README.md](docs/README.md)에서 찾는다. 목적과 범위는 [docs/plan.md](docs/plan.md), 진행 상황은 [docs/roadmap.md](docs/roadmap.md)에 있다.

## 설치와 설정

리눅스(cgroup v2, PSI 활성, 커널 5.14 이상)와 gcc가 필요하다.

```bash
make                # glibc 정적 링크 → build/glibc/tg-sampler, build/glibc/thrash-guard
make LIBC=musl      # musl 정적 링크 (musl-tools 필요)
make test           # 단위 테스트 (ASan/UBSan)
make lint           # cppcheck
```

서비스 파일은 `dry-run`(실제로 종료하지 않고 판단만 기록)으로 시작한다. 실제 종료는 `--no-dry-run` 옵션으로 켠다. 종료 후보 범위와 필수 프로세스 보호 설정은 [packaging/README.md](packaging/README.md)를 따른다.

## 수집기 실행 예

```bash
# VM 밖(수신 측)
python3 lab/collect/tg_receiver.py --port 9999 --out run.log

# VM 안(측정 대상). mlockall에는 root 또는 충분한 RLIMIT_MEMLOCK이 필요하다.
sudo ./tg-sampler --dest <수신기 IP>:9999 --interval-ms 250
```
